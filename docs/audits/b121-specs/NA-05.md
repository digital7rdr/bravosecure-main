# NA-05 - call.answer is abandoned at a fixed 12s budget while the call is still alive; nothing re-sends it and the connecting watchdog is already counting

## Verdict

**CONFIRMED-WITH-DRIFT** — the defect is real and reproducible in the current tree, but the audit's
description of the _mechanism_ ("NO re-send on reconnect") is imprecise: a re-send loop already
exists. The real defect is that its ceiling expires while the call is non-terminal, and that the
callee's 20s death clock starts at `accept()` rather than at answer-delivery.

Evidence (current tree):

- `src/modules/messenger/webrtc/signallingClient.ts:42` — `const CALL_SETUP_SEND_BUDGET_MS = 12_000;`
  and its own doc comment at `:39` claims 12s "stays well inside … the 20s connecting watchdog"
  — i.e. by construction the frame is abandoned **while the call is still ringing/connecting**.
- `src/modules/messenger/webrtc/signallingClient.ts:214-218` — the loop _is_ a re-send-on-reconnect
  mechanism: `const s = (this.transport as unknown as {state?: string}).state; if (s === 'connected'
&& this.trySend(event, data)) {return;} if (Date.now() - t0 >= timeoutMs) {break;} await new
Promise(r => setTimeout(r, 100));`. It polls every 100 ms and lands the frame the moment the socket
  returns — so the audit's "buffer the pending answer and re-send once on the next `connected`" is
  already implemented; only the ceiling is wrong.
- `src/modules/messenger/webrtc/signallingClient.ts:227-229` — after the ceiling the only remaining
  behaviour is one unconditional `trySend` (which throws-and-warns against a closed socket, see
  `packages/messenger-core/src/transport/client.ts:320-322` `if (!this.socket?.connected) {throw new
Error('transport not open');}`) and then `console.warn(... frame dropped)`. Nothing retries after
  that point.
- `src/modules/messenger/webrtc/callController.ts:547-548` —
  `this.opts.signalling.sendAnswer(this.descriptor.callId, this.descriptor.peer, answer.sdp);` then
  `this.setState('connecting');`. `sendAnswer` returns `void`, so the controller cannot know whether
  the frame landed.
- `src/modules/messenger/webrtc/callController.ts:1384-1401` — `setState('connecting')` arms the
  watchdog immediately with `CONNECTING_WATCHDOG_MS` (`:118` = `20_000`), whose expiry calls
  `this.hangup('failed')`. So the callee's death clock starts at accept, not at answer-delivery.
- Nothing else re-sends a 1:1 answer. The only reconnect-edge re-emitter in the call stack is the
  media-state re-assert in `src/modules/messenger/webrtc/useCall.ts:1046-1055`, and that effect is
  gated on `if (state !== 'connected') { … return; }` (`useCall.ts:967`) — it never runs during the
  `connecting` window this bug lives in.

Not already fixed; not refuted.

## Mechanism

1. Callee is woken from a notification / Doze. The WS is down or mid-handshake
   (`TransportClient.state !== 'connected'`).
2. User taps Accept → `CallController.accept()` runs `setRemoteOffer` → `attachLocalMedia` →
   `createAnswerAndApply` → `signalling.sendAnswer(...)` (`callController.ts:547`).
3. `sendAnswer` enqueues `waitOpenThenSend('call.answer', …, CALL_SETUP_SEND_BUDGET_MS, callId)`
   (`signallingClient.ts:285-290`). The loop polls every 100 ms for `state === 'connected'`.
4. `accept()` immediately calls `setState('connecting')` (`callController.ts:548`), which arms the
   20s watchdog (`callController.ts:1384-1401`). The ring timer was already cancelled at
   `callController.ts:512`, so the watchdog is the only timer left.
5. At t = 12 s the loop breaks, makes one unconditional `trySend` — which throws
   `transport not open` and is swallowed into a `console.warn` (`signallingClient.ts:161-169`,
   `227-229`) — and gives up permanently.
6. WS recovers at, say, t = 14 s. Nobody re-sends. The callee sits in `connecting` with no answer on
   the wire.
7. At t = 20 s the watchdog fires `hangup('failed')` → callee shows "Call failed".
8. The caller never received `call.answer`, so it stays in `calling` until its 45s ring timeout
   (`callRingState.ts:33` `DEFAULT_RING_TIMEOUT_MS = 45_000`) and then writes a
   `missed_call_outgoing`. User-visible: "I answered and it said failed; they kept ringing."

The same shape kills a `call.offer` (`signallingClient.ts:269-274`), just with a 45s deadline
instead of 20s — an outage of 12-45 s drops the offer even though the caller is still on "Calling…".

## Fix

Three edits, all client-side. No wire-format change, no schema change, no server change, no
migration, no back-compat surface (nothing new goes on the wire).

**Insertion (new method, placed directly after the block above):**

```ts
  /**
   * NA-05 — abandon a setup frame that is still waiting on a reconnect.
   *
   * `sendHangup` already marks the call, but a controller can go terminal
   * WITHOUT sending one (peer hangup, ICE hard-fail, sign-out teardown). With
   * the setup budget now spanning the whole ring window, an unmarked call
   * could ship an offer/answer for a call that is already dead. Guarded on an
   * live queue so the marker set cannot grow for the life of the process —
   * `enqueueForCall`'s drain handler is what removes it.
   *
   * Note this cannot suppress `call.hangup`: that send deliberately does not
   * pass `callId` into `waitOpenThenSend`, so it is not cancellable.
   */
  cancelPending(callId: CallId): void {
    if (!this.callIdQueues.has(callId)) {return;}
    this.cancelledCalls.add(callId);
  }
```

### Deliberately out of scope (call it out in review, do NOT silently add)

- **Re-arming the caller's ring timer when a late `call.offer` lands.** Symmetric to fix 2
  (`callController.ts:476` `this.ringState.armOutgoing(params.callId);` fires before the offer is on
  the wire), and `CallRingState.arm` already re-arms cleanly (`callRingState.ts:75-96` clears any
  previous handle). Rejected for this increment because it makes the caller's worst-case "Calling…"
  wall 40 s + 45 s = 85 s, which is a product decision, not a bug fix. Without it, an offer that
  lands at t = 25 s still gets the callee 20 s of ring — strictly better than today's drop.
- **Making `sendOffer` return `Promise<boolean>`.** No consumer; adding it would be dead API.
- **A transport `onStateChange` subscription inside `CallSignalling`** (the audit's literal "re-send
  once on the next 'connected'"). `TransportOptions.onStateChange` is a single slot owned by the host
  (`packages/messenger-core/src/transport/client.ts:141`, dispatched at `:1118-1121`), so a second
  subscriber would need a new fan-out. The existing 100 ms poll is the same mechanism with no new
  wiring — do not add the listener.

**What could regress**

1. A cancelled/ended call shipping a stale offer/answer up to 40 s later — mitigated by fix 3
   (`cancelPending` from `end()`); this is the single highest-risk consequence of raising the budget
   and must be pinned by a test.
2. The per-`callId` queue is now held for up to 40 s. `sendHangup` is immune (it does not pass
   `callId` to `waitOpenThenSend`, `signallingClient.ts:351`) and it marks `cancelledCalls` _before_
   enqueuing, so End still takes effect within one 100 ms tick. Re-verify that in the test suite.
3. `cancelledCalls` growth: bounded by the `callIdQueues.has(callId)` guard plus the existing drain
   handler at `signallingClient.ts:253-260`.
4. The watchdog re-arm extends the maximum `connecting` dwell to (answer-land + 20 s) ≤ 60 s. The
   caller's 45 s ring timeout and its resulting `call.hangup` remain the outer bound whenever the WS
   is up — which it must be for the answer to have landed at all.
5. RN freezes JS timers when backgrounded; the loop uses a wall-clock deadline
   (`Date.now() - t0 >= timeoutMs`), so a frozen-then-thawed loop expires immediately on resume
   rather than looping forever. That is the pre-existing behaviour and is fine — but it means the
   40 s is wall-clock, not "40 s of foreground".

## Risk

Things a reviewer should be suspicious of:

1. **Stale-frame window.** Raising 12 s → 40 s is only safe because `end()` now calls
   `cancelPending`. Verify _every_ terminal path reaches `end()` with a live `this.descriptor`:
   `hangup()` (`:559`), peer `call.hangup` (`:346`), ring expire (`:1291`), connecting watchdog
   (`:1400` → `hangup('failed')`), ICE hard-fail, and the `useCall` unmount teardown. If any path
   nulls the descriptor before `end()`, the abandon silently no-ops and a stale offer can ship 40 s
   late.
2. **`cancelPending` must not be able to suppress `call.hangup`.** It relies on `sendHangup` _not_
   passing `callId` into `waitOpenThenSend` (`signallingClient.ts:351`). If someone "tidies" that
   call to pass `callId` for symmetry, hangups become self-cancelling and calls will wedge. Worth a
   `// Why:` guard comment at that line or an explicit test (assertion 5).
3. **Watchdog re-arm could mask a genuinely dead call.** It only re-arms while
   `this.state === 'connecting'` and `this.descriptor?.callId` still matches, and the total dwell is
   bounded by (≤40 s + 20 s). Confirm the guards are checked _inside_ the `.then`, not captured
   before.
4. **Microtask ordering under fake timers.** `delivered` resolves through
   `Promise.resolve().catch().then(async work)` — roughly 4 microtasks. Tests that use
   `await flush(8)` are fine; a test using `await Promise.resolve()` twice is not. Any flaky
   watchdog test is almost certainly this, not a product bug.
5. **`enqueueForCall<T>` generic + `Map<CallId, Promise<unknown>>`.** The drain handler compares
   `this.callIdQueues.get(callId) === next` by identity — still correct, but confirm the `finally`
   still deletes both the queue entry and the `cancelledCalls` marker, or the marker set leaks.
6. **The 40 s number is a judgement call, not a derived constant.** It is chosen to sit under
   `DEFAULT_RING_TIMEOUT_MS = 45_000` (`callRingState.ts:33`). If the ring timeout is ever lowered,
   this must move with it. Consider deriving it from that export instead of a bare literal if the
   reviewer prefers — the trade-off is a new import edge from `signallingClient` to `callRingState`.
7. **No security surface is touched** — `auth` blocks (`CallOfferAuth` / `CallControlAuth`) ride the
   frame unchanged, no verification is relaxed, nothing new is logged (the added warns carry only
   event names and callIds, matching the existing `[bravo.signalling]` lines; no SDP, no key bytes).
   Re-confirm against `packages/messenger-core/__tests__/logAudit.test.ts` anyway.
