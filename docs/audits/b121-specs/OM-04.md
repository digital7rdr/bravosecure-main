# OM-04 - Killed-app FCM msg-wake banners but never fetches; catch-up waits for a manual app open

## Verdict

**CONFIRMED** — both cited sites match by content in the current tree, and the underlying
blocker is worse than the audit states (the warm pull block is not even _registered_ in a
killed-app VM).

- `src/modules/messenger/push/fcmHeadless.ts:150-155` — verbatim: `if (kind === 'msg-wake') {` …
  `// We deliberately do NOT boot the messenger runtime / libsignal / SQLCipher / WS here — that
2nd-VM contention is why the headless task was removed. The decrypted content lands when the
app foregrounds and the WS reconnects`. The block ends at `await showMessageNotif(...)` /
  `console.log('[fcm-headless] msg-wake banner displayed');` then `return;` — **no network call
  of any kind**.
- `src/modules/messenger/push/fcmBootstrap.ts:1591-1612` — the pull the audit points at
  (`rt.pullEnvelopes()` guarded by `catch (e) { console.log('[fcm] msg-wake bg pull skipped:', …) }`)
  lives inside the handler registered at `fcmBootstrap.ts:1400`, a **module-scope** call that only
  runs once something imports `fcmBootstrap` — which only happens when the React tree mounts.
- `index.js:47` — `messaging().setBackgroundMessageHandler(handleHeadlessFcm);` at bundle entry,
  with `index.js:42-46` stating the handler "NEVER boots the messenger runtime, SQLCipher, or the
  WS". In a killed-app headless VM this is the **only** handler installed.
- `src/modules/messenger/runtime/runtime.ts:557` — `throw new Error('production runtime requires
configureMessengerRuntime(cfg) first')`, and `configureMessengerRuntime` is called from exactly
  two places (`src/navigation/MainNavigator.tsx:435`, `src/screens/messenger/BackupRestoreScreen.tsx`).
  So even if `fcmBootstrap`'s handler were reachable headless, `getMessengerRuntime('production')`
  throws.
- `apps/messenger-service/src/relay/envelope.service.ts:318-320` — the sender's ✓✓
  (`envelope.delivered`) is emitted only from `ack()` via the read-then-delete submitter mapping.
  Nothing else advances the tick. Confirms the audit's "sender tick waits for a manual app open".

## Mechanism

1. Sender submits. `EnvelopeController.send` (`envelope.controller.ts`) stores the sealed envelope
   and fires `push.sendChatWake(...)`; `push.service.ts:682` emits data-only FCM
   `{kind:'msg-wake', conversationId, senderUserId}` with `collapseKey: msg-wake:<conv>`.
2. Recipient process is dead. Android boots a headless JS VM which evaluates `index.js` only.
   `messaging().setBackgroundMessageHandler(handleHeadlessFcm)` is installed; `App` is registered
   but never mounted, so `MainNavigator` never runs, so `configureMessengerRuntime` never runs, so
   `fcmBootstrap` is never imported and its richer handler at `fcmBootstrap.ts:1400` never
   overwrites the slim one.
3. `handleHeadlessFcm` hits the `kind === 'msg-wake'` branch, resolves a title from the persisted
   AsyncStorage vault (`mutedLookup.readOwnerConversations`), draws one notifee banner, and
   `return`s. Zero bytes are fetched from the relay.
4. The envelope sits in Redis for up to `RELAY_DWELL_SECONDS` (30 d). The recipient device has
   nothing locally: not the ciphertext, not the plaintext.
5. Nothing changes until the user manually opens the app. Only then does
   `MainNavigator` → `configureMessengerRuntime` → `buildProductionRuntime` → WS open →
   `coalescedDrain` → `drainRelay` (`productionRuntime.ts:7531`) pull, decrypt, persist and
   `relay.ack(...)`. The ack is what triggers `EnvelopeService.ack` → `takeSubmitter` →
   `envelope.delivered`, i.e. the sender's ✓✓.
6. Consequence set: (a) sender's tick is stuck on ✓ for hours/days; (b) if the recipient opens the
   app in a dead zone / airplane mode, the banner they saw yesterday has **no message behind it**
   — the bytes were never fetched while they still had signal.

## Fix

### Honest scoping first (read before implementing)

The audit offers two fixes. **Option 2 ("short FGS boot") is the only one that moves delivery,
ack and the sender tick — and it is architecture-gated and large.** Booting the runtime in a
headless/FGS context in the current tree is blocked by three concrete things:

- `runtime.ts:557` — no `productionConfig` exists headless (needs `ownUserId`, the AsyncStorage-
  pinned `ownerKey`, `authorityPubKeyB64`, token getters — all assembled in `MainNavigator`).
- `MainNavigator.tsx` (`InteractionManager.runAfterInteractions` block, "CRITICAL ORDER" comment):
  the backup-restore probe **must** run before `buildProductionRuntime`, because
  `installIdentity()` auto-creates a fresh Signal identity and destroys the "no local identity"
  signal. A headless boot on a fresh install would permanently strand the user's restore — the
  documented Round-8 / B-107 data-loss class.
- `buildProductionRuntime` (`productionRuntime.ts:423` onward) also publishes the own bundle and
  rotates the signed pre-key — the same side effects `fcmBootstrap.ts:~293` already refuses to
  trigger during restore.

Plus batch architecture constraint **#12 (OR-1) = NOT-COVERED, needs human approval**.

**Option 1 as literally worded ("fetch+persist sealed, NO decrypt") is also wrong on its own**:
without an ack the envelope stays on the relay, the warm drain re-pulls it in <1 s, and the sender
tick does not move — so a naive "prefetch and stage" is pure cost. It becomes worth shipping only
if the staged copy is _consumed_ on the one path where re-pulling is impossible: **the app is open
but the network is gone.**

So this spec ships the **smallest correct increment** — a bounded headless prefetch whose staged
bytes are consumed as a _pull fallback_ inside the existing `drainRelay` loop — and explicitly
defers the sender-tick half to a follow-up that needs an architecture amendment.

What this increment does deliver:

- The ciphertext is on-device the moment the wake lands, so opening the app offline still renders
  the message (protection-officer dead-zone case).
- It is 100 % additive: the happy path (`relay.pull` succeeds) is byte-for-byte unchanged.
- No decrypt, no key material, no SQLCipher, no identity install, no runtime boot in the headless
  VM — nothing in the CLAUDE.md stop-condition list is touched.

What it does **not** deliver (state this in the PR): delivery, ack and the sender ✓✓ still wait
for the app to open. That is the arch-gated follow-up.

### File 1 (new): `src/modules/messenger/push/prefetchedEnvelopes.ts`

Owner-scoped, bounded AsyncStorage stage. Modelled directly on the existing
`src/modules/messenger/push/pendingActions.ts` (same key shape, same read/write/sweep helpers,
same best-effort posture).

```ts
/**
 * OM-04 — sealed-envelope stage written by the KILLED-APP headless FCM handler.
 *
 * The headless VM must not boot the runtime (see index.js), so it cannot decrypt.
 * It can, however, fetch the sealed bytes the relay is holding and park them here
 * so a later app-open that has NO network still has the message.
 *
 * Security: entries hold ONLY the outer sealed-sender wrap — the same opaque
 * ciphertext the relay stores, ECIES-wrapped to this device's identity key
 * (which lives in SQLCipher/Keychain, not here). No ackToken (so nothing here
 * can be used to delete a server-side envelope), no sender, no plaintext, no key
 * material. Bounded by count / bytes / age; cleared on consume and on wipe.
 */
import AsyncStorage from '@react-native-async-storage/async-storage';
import type {RelayEnvelope} from '@bravo/messenger-core';

const BASE_KEY = 'bravo:prefetched-envelopes:v1';
const MAX_AGE_MS = 24 * 60 * 60 * 1000;
const MAX_ENTRIES = 100;
const MAX_BYTES = 1024 * 1024;

interface StagedEnvelope {
  envelopeId: string;
  outerSealed: string;
  timestamp: number;
  ts: number;
}

function keyFor(owner: string): string {
  return `${BASE_KEY}:${owner}`;
}

async function read(owner: string): Promise<StagedEnvelope[]> {
  try {
    const raw = await AsyncStorage.getItem(keyFor(owner));
    if (!raw) {
      return [];
    }
    const arr = JSON.parse(raw);
    return Array.isArray(arr) ? (arr as StagedEnvelope[]) : [];
  } catch {
    return [];
  }
}

export async function stagePrefetchedEnvelopes(
  owner: string,
  envelopes: ReadonlyArray<{envelopeId: string; outerSealed: string; timestamp: number}>,
): Promise<number> {
  if (!owner || !envelopes.length) {
    return 0;
  }
  const now = Date.now();
  const existing = (await read(owner)).filter(e => now - (e.ts ?? 0) < MAX_AGE_MS);
  const byId = new Map(existing.map(e => [e.envelopeId, e]));
  for (const e of envelopes) {
    if (!e?.envelopeId || !e?.outerSealed) {
      continue;
    }
    if (byId.has(e.envelopeId)) {
      continue;
    }
    byId.set(e.envelopeId, {
      envelopeId: e.envelopeId,
      outerSealed: e.outerSealed,
      timestamp: e.timestamp,
      ts: now,
    });
  }
  let out = Array.from(byId.values()).slice(-MAX_ENTRIES);
  while (out.length && JSON.stringify(out).length > MAX_BYTES) {
    out = out.slice(1);
  }
  try {
    await AsyncStorage.setItem(keyFor(owner), JSON.stringify(out));
  } catch {
    return 0;
  }
  return out.length;
}

/**
 * Consumed by drainRelay ONLY when `relay.pull` failed (offline). Shaped as
 * RelayEnvelope so the existing drain loop body needs no change; `ackToken` is
 * deliberately absent — an ack for a staged envelope is expected to fail, the
 * relay keeps its copy, and the next reachable pull acks it via the seen-gate.
 */
export async function loadPrefetchedEnvelopes(owner: string): Promise<RelayEnvelope[]> {
  if (!owner) {
    return [];
  }
  const now = Date.now();
  return (await read(owner))
    .filter(e => now - (e.ts ?? 0) < MAX_AGE_MS)
    .map(e => ({
      envelopeId: e.envelopeId,
      recipient: {userId: owner, deviceId: 1},
      outerSealed: e.outerSealed,
      timestamp: e.timestamp,
      dwellExpires: 0,
    }));
}

export async function clearPrefetchedEnvelopes(owner: string): Promise<void> {
  if (!owner) {
    return;
  }
  try {
    await AsyncStorage.removeItem(keyFor(owner));
  } catch {
    /* best effort */
  }
}
```

### File 2 (new): `src/modules/messenger/push/headlessPrefetch.ts`

```ts
/**
 * OM-04 — bounded, decrypt-free relay catch-up for the KILLED-APP path.
 *
 * Runs inside the headless FCM VM AFTER the banner is drawn. It reuses the
 * shared RelayHttpClient (same auth headers, same 20 s fetch deadline) to pull
 * the sealed envelopes the relay is holding and parks them in
 * prefetchedEnvelopes. It NEVER unwraps, never opens SQLCipher, never touches
 * the identity store, and never acks — so nothing it does can advance a ratchet,
 * delete a server-side envelope, or trip the fresh-install restore probe.
 */
import {RelayHttpClient} from '@bravo/messenger-core';
import AsyncStorage from '@react-native-async-storage/async-storage';
import {MSG_BASE_URL} from '@utils/constants';
import {readOwnUserId} from './mutedLookup';
import {stagePrefetchedEnvelopes} from './prefetchedEnvelopes';

const BUDGET_MS = 12_000;
const PAGE_LIMIT = 50;

let lastRunAt = 0;

export async function prefetchSealedEnvelopes(): Promise<number> {
  const now = Date.now();
  if (now - lastRunAt < 5_000) {
    return 0;
  } // Why: an FCM burst wakes this handler repeatedly
  lastRunAt = now;

  const owner = await readOwnUserId();
  if (!owner) {
    return 0;
  }
  if (!(await AsyncStorage.getItem('auth:refresh_token'))) {
    return 0;
  }

  const relay = new RelayHttpClient({
    baseUrl: MSG_BASE_URL,
    // signalDeviceId is hardcoded to 1 across the app (Phase-1 single-device).
    signalDeviceId: 1,
    getToken: () => AsyncStorage.getItem('auth:access_token'),
    refreshToken: () => {
      const {refreshAccessTokenShared} = require('@services/api') as typeof import('@services/api');
      return refreshAccessTokenShared();
    },
  });

  const work = (async () => {
    const {envelopes} = await relay.pull({limit: PAGE_LIMIT});
    if (!envelopes.length) {
      return 0;
    }
    return stagePrefetchedEnvelopes(
      owner,
      envelopes.map(e => ({
        envelopeId: e.envelopeId,
        outerSealed: e.outerSealed,
        timestamp: e.timestamp,
      })),
    );
  })();

  try {
    return await Promise.race([
      work,
      new Promise<number>(res => setTimeout(() => res(0), BUDGET_MS)),
    ]);
  } catch (e) {
    console.log('[fcm-headless] prefetch skipped:', (e as Error).message);
    return 0;
  }
}
```

Notes on choices a reviewer will ask about:

- `refreshAccessTokenShared` from a headless VM is **already established** in this codebase —
  `pendingActions.sendCallDecline` (called by the slim notifee handler) does exactly this
  (`pendingActions.ts:122-127`). `refreshAccessToken` (`src/services/api.ts:32-42`) only _writes_
  new tokens; the token-clearing lives in the axios interceptor, which is not on this path.
- No restore-mode guard is needed (unlike `fcmBootstrap.ts:~293`) because nothing here touches
  identity, key publication, or SQLCipher. Add one only if `installIdentity` ever moves onto this path.
- `bootstrap` is deliberately **not** passed — the headless path must never claim the 1000-envelope
  bootstrap window nor flip `bravo.relay.bootstrap-done`.

### Schema / wire

- **No SQLCipher schema change.** The stage is AsyncStorage, versioned in the key
  (`bravo:prefetched-envelopes:v1`) so a future shape change is a new key, not a migration.
- **No wire change.** `GET /envelopes` is called exactly as the warm drain calls it, with the same
  headers and no new query params. Server needs no deploy; old servers work unchanged.
- **Old-peer / old-client behaviour:** irrelevant — this is a purely local read-path optimisation
  with no protocol surface.

### Follow-up (architecture-gated, do NOT bundle with this)

To actually move delivery/ack/the sender tick from a killed app you need a _receive-only_ runtime
boot (short FGS or headless) that skips `installIdentity`/`publishOwnBundle`/SPK-rotation and runs
strictly after the backup-restore probe. That requires a written amendment per
`docs/architecture/ARCHITECTURE_AMENDMENT_SFRAME.md` covering: (a) the boot-order guarantee vs the
fresh-install restore probe, (b) SQLCipher open from a background context, (c) JWT/sender-cert
handling with no user present. Track it as its own finding.

Callers that could feel it:

- `mutedLookup` is consumed by `fcmHeadless.ts`, `fcmBootstrap.ts`, and the notifee tap handlers.
  The `parseMemo` shape change is internal; the memo-hit fast path is unchanged.

Overlapping findings — coordinate edits:

- **Any finding editing `drainRelay`** (notably the seen-gate / ack-disposition family and B-30
  `LeaveOnRelayError` work) touches the same loop. This spec only wraps the `relay.pull` call and
  appends a tail block; keep it as the outermost change so the loop body stays mergeable.
- **OM-06 / NA-06 and the notification family** edit `fcmHeadless.ts`'s msg-wake branch. This spec
  appends _after_ the existing `try/catch`, before the `return`, so it should not collide, but
  land it after those if they rewrite the branch.
- **Anything touching `wipeAtRest`** (backup/logout hardening) shares Step 5's neighbourhood.

What could regress:

1. `drainRelay` swallowing a genuine pull failure when a stale stage exists → a real network error
   would be masked. Mitigated by rethrowing when the stage is empty, and by clearing the stage
   unconditionally after the offline pass.
2. Headless budget: the prefetch adds up to 12 s to the msg-wake handler. It runs _after_ the
   banner, so the user-visible latency is unchanged, but a very slow network could let Android tear
   the VM down mid-fetch (harmless — nothing is persisted until the whole page resolves).
3. Token refresh from headless rotates the refresh token. Already done by
   `pendingActions.sendCallDecline`, but now on a much more frequent trigger. Watch for
   refresh-token-rotation races if the server ever enforces single-use refresh tokens.
4. Relay throttle: `GET /envelopes` is capped at 120/10 s per user (`envelope.controller.ts`).
   The 5 s in-VM debounce plus FCM's `collapseKey` keeps this far under budget, but a burst of
   wakes across a VM-restart loop bypasses the in-memory debounce (module state dies with the VM).

## Risk

Things a reviewer should be suspicious of:

1. **Error masking in `drainRelay`.** The new `catch (pullErr)` must rethrow whenever the stage is
   empty, and the offline pass must `return` after clearing — otherwise a persistent outage turns
   into a silent, repeatedly-successful drain and the WS/AppState retry ladder stops firing.
2. **Ack semantics.** Staged rows deliberately carry no `ackToken`. Verify no code path acks them
   with a synthesised token and that `ackStrictMode` on the server would reject such an ack anyway
   (`envelope.service.ts:44-53`). The invariant "ack ⇒ hard-delete ⇒ ✓✓ ⇒ the device really has it"
   must survive intact.
3. **Double-decrypt / ratchet corruption.** The offline pass funnels through the _same_ loop body,
   so `seenEnvelopes.wasSeen` + `inFlightEnvelopes` still gate it. Confirm the staged envelopes'
   `envelopeId`s are the real server ids (they are — copied verbatim from the pull response), not
   regenerated, or the dedup gate silently stops working.
4. **At-rest posture.** AsyncStorage is not SQLCipher. The justification is that the stage holds
   only the outer sealed wrap — identical bytes to what Redis holds server-side, openable only with
   the identity private key in Keychain/SQLCipher. If anyone later adds `ackToken`, `senderUserId`
   or an unwrapped body to this record, the justification collapses; the test asserting the exact
   persisted key set is the guard.
5. **Headless token refresh.** New, more frequent use of `refreshAccessTokenShared` outside a
   foreground session. It is precedented (`pendingActions.sendCallDecline`) and never clears
   tokens, but it does touch the "auth tokens / session storage" stop-condition area — worth an
   explicit sign-off line in the PR, and it is the one piece that could be dropped (accepting that
   the prefetch then only works within the 15-min access-token window) if the architecture owner
   objects.
6. **Overclaiming.** Do not let the PR description say this fixes the sender tick or "killed-app
   delivery". It does not. It fixes "banner with nothing behind it when you open offline" and
   nothing more.
