# OM-03 — HTTP-submitted 1:1 envelopes never get a delivered/undeliverable receipt

## Verdict

**CONFIRMED** (mechanism exactly as described; the audit's _proposed fix_ is the forbidden
one — see §Fix for the compliant replacement).

Evidence from the current tree:

1. `apps/messenger-service/src/relay/envelope.controller.ts:74-83` — the HTTP submit path
   builds the service input with **no `submitter`**:
   ```
   // Sealed Sender: we intentionally do NOT pass caller identity into
   // the service — the server must not link the stored envelope to
   // the submitter. …
   const res = await this.envelopes.submitEnvelope({
     recipient:    dto.recipient,
     outerSealed:  dto.outerSealed,
     clientMsgId:  dto.clientMsgId,
     expiresAtSec: dto.expiresAtSec,
   });
   ```
2. `apps/messenger-service/src/relay/envelope.service.ts:234-236` — the submitter mapping is
   written **only when the caller supplied one**: `if (input.submitter) { await
this.store.storeSubmitter(envelopeId, input.submitter, effectiveTtl); }`.
   Only `apps/messenger-service/src/gateway/messenger.gateway.ts:1094`
   (`submitter: {userId: ctx.claims.sub, deviceId: ctx.signalDeviceId}`) ever sets it.
3. `apps/messenger-service/src/relay/envelope.service.ts:376-392` — the ack path is fully
   gated on that mapping: `const submitter = await this.store.takeSubmitter(envelopeId); if
(submitter) { … 'envelope.undeliverable' … 'envelope.delivered' … }`. Null submitter ⇒
   **no emit, and no `addPendingDelivered` / `addPendingUndeliverable` queue entry either**,
   so even the RELAY-C3 offline-receipt replay can never carry it.
4. `apps/messenger-service/src/relay/envelope.store.ts:337` documents the resulting hole in
   `takeSubmitter`: _"a missing key returns null (the most common reason is a sender that
   submitted via HTTP …)"_.
5. Client side, the bubble is fully wired and just starves: `productionRuntime.ts:2890-2905`
   (ack-watchdog `httpFallback`) and `:7476-7499` (`drainOutbox`) both call `relay.send(...)`,
   store `r.envelopeId` via `updateMessageEnvelopeId` and set status `'sent'` — and the only
   things that can advance past `'sent'` are `applyEnvelopeDelivered` /
   `applyEnvelopeUndeliverable`, which are reachable **only** from the WS frame switch at
   `productionRuntime.ts:5134-5147`.
6. Blast is wider than the finding states: `resendUndeliverable` (B-46 auto-recovery,
   `productionRuntime.ts:827`) is driven from that same `envelope.undeliverable` case, so an
   HTTP-submitted message destroyed by recipient identity churn gets **no auto-resend either**
   — it dies silently behind a single tick.

### Note on the audit's proposed fix (and the batch architecture ruling)

The audit says _"pass `{userId, deviceId}` submitter on the HTTP POST (same transient
TTL-bounded mapping the WS lane uses)"_. Per the batch architecture constraint this is
**FORBIDDEN as literally proposed** (`MESSENGER_BACKEND.md:137` — JWT is _"rate-limit only —
we do NOT persist submitter identity"_), allowed only as an **anonymous capability handle**.

Honest correction to the constraint's stated rationale, which a reviewer will hit: the claim
that _"on WS the association is an in-memory socket binding that dies with the connection"_ is
**not true of the current tree**. `storeSubmitter` (`envelope.store.ts:316-326`) writes
`submitter:{envelopeId} = "{userId}:{deviceId}"` into **Redis** with the envelope's dwell TTL,
and `addPendingDelivered` (`:373-386`) writes `delivered-pending:{senderUserId}` with a
**7-day** TTL. So an at-rest sender↔envelope linkage already exists on the WS lane. That does
**not** license extending it to HTTP (two wrongs), but it is a **pre-existing compliance
finding worth filing separately**. This spec deliberately does not touch it: the WS lane is
out of OM-03's scope and changing it is a behaviour regression + an architecture question.

## Mechanism

1. User sends a 1:1 message. `productionRuntime` seals it, enqueues an outbox row, and fires
   `transport.send({event: 'envelope.send', …})` over WS with a 5 s ack watchdog
   (`productionRuntime.ts:2936-2957`).
2. WS is down / Doze-frozen / half-dead, so `envelope.accepted` never arrives (or the send
   throws outright). The watchdog runs `httpFallback` → `relay.send(...)` →
   `POST /envelopes`.
3. `EnvelopeController.send` calls `submitEnvelope` **without `submitter`**, so
   `envelope.service.ts:234` skips `storeSubmitter`. Nothing anywhere records who submitted.
4. Client flips the bubble to `'sent'` (single tick) and records `envelope_id`.
5. Recipient comes online, pulls, decrypts, and `POST /envelopes/:id/ack`.
6. `EnvelopeService.ack` hard-deletes, then `takeSubmitter(envelopeId)` returns `null`
   (`envelope.store.ts:339`). The `if (submitter)` body at `:377-392` is skipped entirely:
   no live `envelope.delivered` emit, **and no `delivered-pending` queue entry**, so
   `flushPendingDelivered` on the sender's next connect has nothing to replay either.
7. Sender's bubble is stuck at `'sent'` **forever** — it can never reach `delivered`, and the
   read-receipt path is the only escape hatch (which only fires if the recipient actually
   opens the chat).
8. Same path with `disposition: 'discarded'`: `envelope.undeliverable` is likewise
   unroutable, so `applyEnvelopeUndeliverable` never runs, `resendUndeliverable` never runs,
   and a message destroyed by recipient identity churn is **silently lost behind a tick**.

This is not an edge case: it is the _entire_ ack-watchdog fallback path, the _entire_
`drainOutbox` reconnect path (every message queued during an offline stretch), and the B-46
auto-resend recovery path.

## Fix

**Shape: an anonymous, capability-gated delivery receipt the sender polls.** The relay stores
`rcpt:{envelopeId} = sha256hex(retractToken)[|outcome]` — a per-envelope opaque slot that
carries **no user id, no device id, nothing identity-bearing**. Entitlement is the capability
token the submitter already received at submit, exactly the model
`MESSENGER_SPEC_COVERAGE.md:140` prescribes ("Capability tokens sidestep it cleanly") and
exactly what `POST /envelopes/retract` already does (`envelope.controller.ts:186` — _"Does NOT
use `@CurrentCaller` intentionally — the capability token is the only auth needed here"_).

**Why reuse `retractToken` rather than mint a second token:** the sender already persists it
per message (`messages.retract_token`, populated on both 1:1 HTTP paths via
`updateMessageRetractToken` at `productionRuntime.ts:2896` and `:7488`), so **no SQLCipher
schema bump and no new column are needed**. That matters here specifically: `messages` rows
are mirrored to the backup and hashed by `versionHash` →
`JSON.stringify(serializeMessage(msg))` (`src/modules/messenger/backup/messageMirror.ts:434`),
which includes `retract_token`. Adding a serialized field changes **every row's** version hash
and triggers a whole-history re-mirror on next boot — the exact B-94 `root_mismatch` factory
that `docs/runbooks/BACKUP_LOOP.md` exists to prevent. The relay stores only the SHA-256
_digest_, so a Redis dump yields no retract capability (unlike the existing `retract:{token}`
key, which is keyed by the raw token today). See §Risk for the capability-coupling tradeoff
and the follow-up if a reviewer wants strict separation.

```ts
  /**
   * OM-03 — open a delivery-receipt slot for an envelope whose submitter
   * has no live socket (every HTTP submit). Shares the envelope's dwell
   * TTL: an envelope that ages out takes its receipt with it.
   */
  private static readonly RECEIPT_SETTLED_TTL_SEC = 7 * 24 * 3600;

  async openReceipt(envelopeId: string, retractToken: string, ttlSeconds: number): Promise<void> {
    await this.redis.client.set(
      receiptKey(envelopeId), receiptDigest(retractToken), 'EX', ttlSeconds,
    );
  }

  /**
   * OM-03 — stamp the terminal outcome on an open receipt. No-op when no
   * receipt was opened (WS submits, legacy clients), so this costs one
   * GET on the ack path and nothing else. The settled value gets its own
   * 7-day TTL — the same window `delivered-pending` uses — so a sender
   * that stays offline past the envelope's dwell still collects it.
   */
  async settleReceipt(envelopeId: string, outcome: 'delivered' | 'discarded'): Promise<void> {
    const raw = await this.redis.client.get(receiptKey(envelopeId));
    if (!raw) return;
    const stored = raw.split('|')[0];
    await this.redis.client.set(
      receiptKey(envelopeId),
      `${stored}|${outcome}`,
      'EX', EnvelopeStore.RECEIPT_SETTLED_TTL_SEC,
    );
  }

  /**
   * OM-03 — capability-gated read. A wrong token and an unknown envelope
   * return the SAME `'unknown'`, so this is not a delivery oracle. The
   * digest comparison is constant-time (mirrors `verifyAckToken`).
   */
  async readReceipt(envelopeId: string, presentedToken: string): Promise<ReceiptOutcome> {
    const raw = await this.redis.client.get(receiptKey(envelopeId));
    if (!raw) return 'unknown';
    const [stored, outcome] = raw.split('|');
    const a = Buffer.from(stored, 'utf8');
    const b = Buffer.from(receiptDigest(presentedToken), 'utf8');
    if (a.length !== b.length || !timingSafeEqual(a, b)) return 'unknown';
    return outcome === 'delivered' || outcome === 'discarded' ? outcome : 'pending';
  }
```

### 7. NEW `src/modules/messenger/runtime/httpReceiptReconcile.ts`

Lives in its own module for the reason stated verbatim in `envelopeDelivered.ts:4-9` (the
`messenger-crypto` Jest project runs under Node and cannot require `op-sqlite` via
`productionRuntime`).

```ts
/**
 * OM-03 — reconcile delivery ticks for envelopes submitted over HTTP.
 *
 * The relay can push `envelope.delivered` only to a submitter it has a
 * live-socket mapping for, and Sealed Sender forbids recording who
 * submitted over HTTP. So every ack-watchdog fallback and every outbox
 * drain produced a bubble permanently stuck at single tick. The sender
 * instead polls an anonymous, capability-gated receipt slot with the
 * retract token it already persisted for that message.
 */

import {useMessengerStore} from '../store/messengerStore';
import type {RelayReceiptOutcome} from '@bravo/messenger-core';
import {applyEnvelopeDelivered} from './envelopeDelivered';
import {applyEnvelopeUndeliverable} from './decryptFailureSignal';
import type {LocalMessage} from '../store/types';

export interface ReceiptProbe {
  envelopeId: string;
  retractToken: string;
}

/** Matches the server's settled-receipt TTL — older rows can only answer 'unknown'. */
const RECEIPT_WINDOW_MS = 7 * 24 * 3600 * 1000;
const MAX_PROBES = 100;

/**
 * Pure selector — exported for tests. Candidates are OUR OWN messages
 * still at single tick that carry both an envelope id and a retract
 * token (the pair the HTTP send path records). `skip` holds ids the
 * relay already answered `'unknown'` for, so a dead slot is asked once.
 */
export function selectReceiptProbes(
  messages: Record<string, LocalMessage[]>,
  nowMs: number,
  skip: ReadonlySet<string>,
): ReceiptProbe[] {
  const out: ReceiptProbe[] = [];
  for (const list of Object.values(messages)) {
    for (const msg of list) {
      if (msg.sender_id !== 'self') {
        continue;
      }
      if (msg.status !== 'sent') {
        continue;
      }
      if (!msg.envelope_id || !msg.retract_token) {
        continue;
      }
      if (skip.has(msg.envelope_id)) {
        continue;
      }
      const at = Date.parse(msg.created_at);
      if (!Number.isFinite(at) || nowMs - at > RECEIPT_WINDOW_MS) {
        continue;
      }
      out.push({envelopeId: msg.envelope_id, retractToken: msg.retract_token});
    }
  }
  return out.slice(-MAX_PROBES);
}

const unknownEnvelopeIds = new Set<string>();
let receiptsUnsupported = false;
let inflight = false;

/** Test/logout hook — clears the per-session probe memo. */
export function resetReceiptReconcile(): void {
  unknownEnvelopeIds.clear();
  receiptsUnsupported = false;
  inflight = false;
}

export async function reconcileHttpReceipts(deps: {
  fetchReceipts: (
    items: ReceiptProbe[],
  ) => Promise<{receipts: Array<{envelopeId: string; outcome: RelayReceiptOutcome}>}>;
  isOurEpoch: () => boolean;
  onUndeliverable?: (envelopeId: string) => void;
}): Promise<void> {
  if (receiptsUnsupported || inflight || !deps.isOurEpoch()) {
    return;
  }
  const probes = selectReceiptProbes(
    useMessengerStore.getState().messages,
    Date.now(),
    unknownEnvelopeIds,
  );
  if (probes.length === 0) {
    return;
  }
  inflight = true;
  try {
    const res = await deps.fetchReceipts(probes);
    if (!deps.isOurEpoch()) {
      return;
    }
    for (const r of res.receipts) {
      switch (r.outcome) {
        case 'delivered':
          applyEnvelopeDelivered(r.envelopeId);
          break;
        case 'discarded':
          applyEnvelopeUndeliverable(r.envelopeId);
          deps.onUndeliverable?.(r.envelopeId);
          break;
        case 'unknown':
          unknownEnvelopeIds.add(r.envelopeId);
          break;
        default:
          break;
      }
    }
  } catch (e) {
    if ((e as {status?: number}).status === 404) {
      receiptsUnsupported = true;
    }
  } finally {
    inflight = false;
  }
}
```

| Old client → new server                                              | Omits `receipt`; `input.receipt` is falsy; no `rcpt:` key is written; ack path's `settleReceipt` GET misses and no-ops. **Byte-identical to today.**                                                                                                                                                                                                             |
| New client → old server (server deploys first, so this is transient) | `POST /envelopes` ignores the unknown `receipt` field (class-validator whitelist is not enabled on this DTO — verify before merge; if it is, the field must be added to the DTO _before_ clients ship, which this spec does). `POST /envelopes/receipts` → 404 → `receiptsUnsupported = true`, polling stops for the session. **Degrades to today's behaviour.** |

## Blast radius

**Server** — `envelope.controller.ts` (`send`, new `receipts` route, 2 new DTO classes),
`envelope.service.ts` (`submitEnvelope`, `ack`, new `readReceipts`), `envelope.store.ts`
(3 new methods, 2 new module helpers, `purgeRecipientQueue` DEL list), `envelope.types.ts`,
`dto/send-envelope.dto.ts`. One extra Redis key per HTTP submit that opts in (small string,
dwell-bounded), one extra GET per ack. `EnvelopeService.ack` is called from both
`envelope.controller.ts:172` and the WS `envelope.ack` handler in `messenger.gateway.ts` —
both get the settle step, which is a no-op for WS-submitted envelopes.

**Client** — `packages/messenger-core/src/transport/relayClient.ts` (+ its `index.ts`
re-export), new `src/modules/messenger/runtime/httpReceiptReconcile.ts`, 4 anchor edits in
`productionRuntime.ts`. `applyEnvelopeDelivered` / `applyEnvelopeUndeliverable` /
`resendUndeliverable` are reused **unchanged** — the reconcile path is just a second caller of
the existing, already-idempotent handlers.

**Overlapping findings**

- **MSG-03 / group ticks** — touches the same three `relay.send` sites. Group receipts are
  explicitly out of scope here; if MSG-03 lands per-peer receipt tracking it should extend
  `selectReceiptProbes`, not fork it.
- **SRV-01/GF-1 (`/envelopes/batch`)** — same controller and throttle block; expect a textual
  conflict in the decorator region.
- **OM-02 / OM-05** — same `productionRuntime` send region (`httpFallback`, `drainOutbox`);
  merge order matters, semantics do not overlap.
- **B-46 `undeliverableResend`** — this fix _activates_ a path that has been dormant for HTTP
  sends. Anything latent in `selectUndeliverableResend` will start firing.

**What could regress**

1. **B-46 auto-resend wakes up on a new path.** Messages destroyed by recipient identity churn
   and submitted over HTTP will now trigger one automatic re-send each. That is the intended
   recovery, but it is new traffic on a path that has never run in production. The
   one-attempt budget lives in `undeliverableResend.ts` — confirm it is per-envelope and
   persisted, not per-process, before shipping.
2. **A bubble can now move backwards from the user's view** (`sent` → `undelivered`) minutes
   after the fact. `applyEnvelopeUndeliverable` already guards `read`; verify the ChatScreen
   retry chip renders sanely for a message the user scrolled past.
3. **Poll cost.** 100 ids × the 60 s timer per active sender. Bounded by `MAX_PROBES`, the
   7-day window, the `unknownEnvelopeIds` memo (which prunes dead slots after one ask), and
   the 30/10 s throttle. Watch the throttle interaction on a device that also drains a large
   outbox — both share the per-user bucket.
4. **`purgeStaleRecipientQueue`** now needs the `rcpt:` DEL; if that is missed, purged
   envelopes leave orphan receipt keys dwelling up to 30 days (leak, not a correctness bug).

## Risk

**What a reviewer should be suspicious of, in order:**

1. **"Is this Sealed Sender or not?"** The stored value must be audited by eye: `rcpt:{id}` is
   a SHA-256 hex digest, never a userId, never a deviceId, never the raw token. Ask for the
   Redis-content assertion in the spec test. The failure mode is someone later "simplifying"
   `openReceipt` into `storeSubmitter` — which is exactly the forbidden fix.
2. **Capability coupling.** The receipt poll now presents the retract token. Whoever can read
   a receipt can also retract that message. This does not widen the _server's_ power (it
   minted the token) and does not widen a Redis dump's power (the digest is stored, whereas
   `retract:{token}` is keyed by the raw token today) — but it does mean the poll request
   carries retract authority on the wire. **Follow-up if a reviewer wants strict capability
   separation:** mint a distinct `receiptToken` in `SendEnvelopeResult`, add a
   `messages.receipt_token` column (SCHEMA_VERSION 14 → 15, one idempotent
   `ALTER TABLE messages ADD COLUMN receipt_token TEXT` appended to the `DDL` array in
   `src/modules/messenger/crypto/db.ts`), and — critically — **do NOT add it to
   `serializeMessage`**, or `versionHash` (`messageMirror.ts:434`) changes for every row and
   the next boot re-mirrors the entire history (B-94 `root_mismatch` class).
3. **The JWT is still on the request.** `JwtHttpGuard` runs at the controller level for
   `receipts` (as it does for `retract`), so an adversarial relay _could_ correlate
   `claims.sub` with the envelope ids in the body. That is a logging/telemetry discipline
   question, identical to the one `retract` already carries, and it is _transient_ rather than
   at-rest. Nothing in this change persists the pairing. Confirm no request-body logging is
   added to the new route.
4. **Ack-path ordering.** `settleReceipt` is placed in its own try _before_ the submitter
   block. If a reviewer moves it inside the existing try, a `takeSubmitter` throw will swallow
   the receipt and OM-03 silently comes back for the subset of envelopes that have both.
5. **`'pending'` vs `'unknown'` conflation.** If someone "helpfully" makes a bad token return
   `'pending'` (or a distinct error), the endpoint becomes a delivery oracle for guessed
   envelope ids. The test in §Tests is the lock.
6. **The audit's own line "envelope.undeliverable is unroutable" understates the damage** —
   the real cost is that B-46's auto-resend never runs for HTTP sends. Reviewers scoping this
   as "cosmetic tick" will under-prioritise it; it is silent message loss on the recovery path.
7. **This is not a one-liner.** ~6 server files + 3 client files + a new module + a new HTTP
   route. If the batch needs a smaller increment: ship §1–§5 (server, fully back-compatible
   and inert until a client asks) in one wave, and §6–§8 (client poll) in the next.
