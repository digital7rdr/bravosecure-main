# OM-05 - Drain-time re-seal re-mints `aad.ts = Date.now()`, so receivers order the message at drain time while the sender keeps compose time

## Verdict

**CONFIRMED** (with drift on scope: the audit says "deferred messages"; there are in fact **four** re-seal
sites with the same defect, and the receive-side ordering key is `aad.ts` in **three** places, not one).

Evidence from the current tree:

1. `src/modules/messenger/runtime/productionRuntime.ts:786-798` — the re-seal callback:

   ```ts
   const resealDeferredGroupRow: ResealDeferredFn = async (row, payload) => {
     ...
     aad: {
       to:             peer,
       ts:             Date.now(),          // ← line 797
   ```

   Its own docstring at `:783-785` admits it: _"re-seals the stored group body to THIS peer with a
   **FRESH AAD timestamp** (the re-send is happening now)"_.

2. Receiver uses `aad.ts` as the ordering key — `productionRuntime.ts:7232` (group) and `:7293` (1:1):

   ```ts
   created_at:       new Date(typeof unwrapped.aad?.ts === 'number' ? unwrapped.aad.ts : Date.now()).toISOString(),
   ```

   and `:6204` for the pending-group-stash drain (`sealed.aad.ts`). The `:7228` comment is explicit:
   _"Audit MSG-09 — stamp SEND time from the authenticated aad.ts … so a message drained after
   reconnect sorts by when it was SENT, not when it was received."_ The drain-side re-mint defeats
   exactly that.

3. Sender keeps compose time — `productionRuntime.ts:2385` `const sentAt = new Date().toISOString();`
   is written into the local bubble at `:2441` (group) and `:2781` (1:1). It is never revised, so once
   the row is re-sealed hours later the two devices hold permanently different `created_at` for the
   same `clientMsgId`.

4. The re-seal path is **not** only the A4 deferred case. `drainOutbox` also routes SN-06 stale-cert
   rows through the same callback (`productionRuntime.ts:7449-7466`), so an ordinary group message
   queued through any offline stretch longer than the ~1h cert TTL gets its timestamp rewritten too.

5. Two more sites in the same class: `resendUndeliverable` (`:856`, B-46 1:1 re-send of an
   already-composed message) and the flag-gated resend-protocol replay (`:2255`, resends rows up to
   10 min old) both stamp `ts: Date.now()` while the sender's bubble keeps its original `created_at`.

## Mechanism

1. User sends a group message at T0. `sentAt = new Date()` → local bubble `created_at = T0`
   (`:2385`, `:2441`). `sealedTs = Date.now()` ≈ T0 is stamped into `aad.ts` for every live
   recipient (`:2482`, `:2545`).
2. For one recipient the pre-ship crypto throws (peer unprovisioned / OPK pool exhausted /
   keys-service blip), so `sendOne` writes a **deferred** outbox row carrying only the group-wrapped
   `sealedBody` and no `outerSealed` (`:2565-2593`). `outbox.created_at` is stamped `Date.now()` ≈ T0
   by `SqlOutboxStore.enqueue` (`src/modules/messenger/store/sqlOutboxStore.ts:80-95`).
   _Alternative entry:_ the row ships fine but the device goes offline; on the next drain
   `isStoredCertStale(payload.certExpSec)` is true and the row takes the same re-seal branch.
3. Hours later (reconnect, boot drain, or the 45s timer at `:1613`) `drainOutbox` calls
   `reseal(...)` → `resealDeferredGroupRow` mints a fresh cert and seals with
   `aad.ts = Date.now() = T1`.
4. The recipient decrypts, `verifySealedAad` passes (T1 is "now", so neither `stale` nor `future`),
   and the row lands with `created_at = T1` (`:7232`). `appendMessage` binary-splices it into the
   thread at position T1 — after every message actually sent between T0 and T1.
5. Result: sender's thread shows the message at T0; that one recipient shows it at T1. Nothing ever
   reconciles the two — `created_at` is never re-derived, and the backup mirror persists the divergent
   value on each side. In a group, member A (live delivery, ts=T0) and member B (deferred, ts=T1) also
   disagree with **each other**.

Failure is silent and permanent; the only visible symptom is "his reply appears above my question"
on one device and not the other.

## Fix

Chosen approach: **reuse the compose timestamp the outbox already persists as `aad.ts` on re-seal**,
clamped so it can never fall outside the receiver's existing accept window.

Why not the "doc-safe alternative" of carrying compose time as a new `SealedPayload` field: it is a
**fleet-breaking wire change**. `isSealedPayload` in
`packages/messenger-core/src/crypto/sealedSender.ts:602-607` rejects **any unknown top-level key**:

```ts
for (const k of Object.keys(o)) {
  if (!SEALED_PAYLOAD_KEYS.has(k)) {
    return false;
  }
}
```

and `:672-676` does the same for unknown `aad` keys. A shape rejection throws `CryptoError` out of
`unsealPayload`, which `productionRuntime.ts:6388-6396` unconditionally rethrows; the drain catches it
at `:7852-7862` and acks **`discarded`** (`:7876`). So every message from an upgraded sender to a
not-yet-upgraded receiver would be **destroyed on the relay, not deferred**. A new payload field
therefore needs a two-release rollout (tolerant receivers first, emitting senders second) — strictly
worse than reusing `aad.ts`, which needs no wire change at all, no schema change, and is understood
by every deployed client.

Note the change **narrows** the accept window (an older `ts` is closer to the `stale` bound, never
closer to `future`); it does not weaken `verifySealedAad`, does not touch the envelope shape or the
AAD key set, and re-seal keeps fetching a **fresh** sender cert (`certCache.get()` at `:789`).
Because it re-interprets `SealedAad.ts` from "when this seal ran" to "when the sender composed this
message", it still trips the CLAUDE.md _AAD binding_ stop condition → **architecture sign-off
required before implementing** (see Risk).

### 1. NEW FILE — `src/modules/messenger/runtime/outboxResealTimestamp.ts`

Follows the `outboxCertFreshness.ts` pattern exactly: a tiny pure decision module so it is unit
testable in the node-env `messenger-crypto` Jest project without standing up the RN runtime.

```ts
/**
 * OM-05 — which timestamp a RE-SEALED outbox envelope carries in `aad.ts`.
 *
 * The receiver stamps `created_at` from `aad.ts` (productionRuntime receive
 * path), while the sender's bubble keeps its compose time. Re-minting
 * `Date.now()` at drain therefore left the two devices permanently disagreeing
 * on where the message belongs in the thread. The outbox already persists the
 * compose moment as `outbox.created_at`, so the drain can carry it instead.
 *
 * The clamps exist because `aad.ts` is still an accept-window input:
 * `verifySealedAad` rejects `stale` beyond SEALED_AAD_MAX_AGE_MS and `future`
 * beyond SEALED_AAD_FUTURE_MS. A row that outlived the dwell window, or a
 * device whose clock jumped backwards, must fall back to "now" — shipping an
 * envelope the receiver destroys is worse than shipping one ordered late.
 */

import {SEALED_AAD_MAX_AGE_MS} from '@bravo/messenger-core';

/**
 * How far inside the stale bound a carried timestamp must stay. Covers the
 * drain's own round-trip plus receiver clock skew.
 */
export const RESEAL_TS_SAFETY_MARGIN_MS = 60 * 60 * 1000;

export function resolveResealAadTs(
  composedAtMs: number | undefined,
  nowMs: number = Date.now(),
): number {
  if (typeof composedAtMs !== 'number' || !Number.isFinite(composedAtMs)) {
    return nowMs;
  }
  if (composedAtMs > nowMs) {
    return nowMs;
  }
  if (composedAtMs < nowMs - (SEALED_AAD_MAX_AGE_MS - RESEAL_TS_SAFETY_MARGIN_MS)) {
    return nowMs;
  }
  return composedAtMs;
}
```

## Blast radius

**Files**

- `src/modules/messenger/runtime/productionRuntime.ts` — 1 import, 1 type widening, 2 call sites,

**Functions**

- `resealDeferredGroupRow` (implementation of `ResealDeferredFn`) — the only implementation; verified
  by grep, the type appears only at `:786` and `:7388`.
- `drainOutbox` — invoked at `:1134` (reconnect), `:1601` (boot) and `:1613` (45s timer); all three
  pass `resealDeferredGroupRow`, so the widened row shape flows through unchanged.
- `resendUndeliverable`, `setResendSignalHandler` closure.

**Receive side** — not edited, but this is where the effect lands: `:6204`, `:7232`, `:7293`
(`created_at` from `aad.ts`) and `messengerStore.appendMessage`'s chronological splice.

**Overlapping findings**

- **OM-02** (clamp display timestamp to the server envelope ts on large skew) edits the _same three_
  `created_at:` expressions. Land OM-02 after this, and make it a clamp on the value derived from
  `aad.ts` — not a replacement of it, or OM-05's carried compose time is thrown away.
- **GF-2 / SYNC-2** (durable group key fan-out) adds rows to the same outbox and may add new
  `payload` kinds through `drainOutbox`; keep `row.createdAt` threading in any new re-seal branch.
- **SN-06** (`outboxCertFreshness.ts`) shares the stale-cert branch this change touches.
- **OM-06** and any other `drainOutbox` edit will conflict textually around `:7420-7470`.

**What could regress**

1. A row that legitimately sits in the outbox longer than `SEALED_AAD_MAX_AGE_MS - margin` would be
   destroyed on arrival as `stale` if the clamp were missing. The clamp exists precisely for this;
   the test below pins it. (Practically bounded: `MAX_ATTEMPTS = 10` in `sqlOutboxStore.ts:59`, but
   SN-04 unreachable failures do not consume the budget, so an offline device _can_ hold a row
   indefinitely — the clamp is not theoretical.)
2. Backwards device clock: `outbox.created_at` ahead of `Date.now()` would risk a `future` reject.
   Clamped to `now`.
3. Disappearing messages: `expiresAtSec` is carried verbatim from the payload and is **not** derived
   from `aad.ts` (`:7234`, `:7295` read `unwrapped.expiresAtSec`). Unchanged.
4. Backup mirror / Merkle: `created_at` values on _newly received_ rows change relative to the
   pre-fix build, but this is a receive-side value written once at insert; no re-write of existing
   rows, so no mirror drift and BACKUP_LOOP I1–I9 are untouched.
5. Media sends via `sendMedia(existingMsgId)` retain a pre-existing, unrelated skew: the bubble is
   appended before upload while the outbox row is created after it. Out of scope for OM-05; worth a
   separate follow-up if the founder reports media ordering specifically.

## Risk

1. **Architecture gate is real.** This re-interprets `SealedAad.ts` from "when `seal()` was called"
   (its literal docstring, `packages/messenger-core/src/crypto/sealedSender.ts:162-163`) to "when the
   message was composed". CLAUDE.md lists _AAD binding_ as a stop condition. The change does not
   weaken any check and adds no wire field, but a reviewer should insist on the sign-off before the
   diff lands, and on updating the `SealedAad.ts` docstring so the contract and the code agree.
2. **The clamp is the whole safety argument.** A reviewer should verify `resolveResealAadTs` is
   applied at _every_ re-seal site and that no caller passes an unclamped value straight into
   `aad.ts`. A missed site turns a delayed message into a `stale` reject, which the receive path
   destroys **silently and with no placeholder** (`productionRuntime.ts:6494-6500`) — a strictly
   worse failure than the bug being fixed.
3. **Do not let this become a window widening.** If anyone proposes raising
   `SEALED_AAD_MAX_AGE_MS` (or passing `maxAgeMs`) to make older rows land, that is FORBIDDEN under
   "never weaken transitions" — the clamp's fallback-to-now is the sanctioned escape.
4. **Anti-replay reasoning.** `aad.ts` is _not_ the replay defense (the ratchet's single-use message
   keys plus `SeenEnvelopeStore` are — stated at `sealedSender.ts:366-371`), and an older `ts` moves
   the envelope _closer_ to rejection, never further. A reviewer who believes this widens a replay
   window should be pointed at those lines.
5. **Watch for the OM-02 collision.** Both findings edit the `created_at:` expressions at `:6204`,
   `:7232`, `:7293`. Landing OM-02 first, or landing it as a _replacement_ of the `aad.ts` read
   rather than a clamp on it, silently reverts OM-05.
6. **The audit's implied "add `sentAtMs` to the outbox payload / envelope" is the wrong fix** and a
   reviewer should reject it if it appears: the strict `SEALED_PAYLOAD_KEYS` whitelist makes any new
   sealed field a hard reject on every not-yet-upgraded client, and that reject path acks
   `discarded`, i.e. permanent message loss during rollout. Carrying `outbox.created_at` needs no
   wire change and no migration.
7. **Not covered by this fix:** the sender's own bubble is still never revised, so a message the
   sender composes while their clock is wrong stays wrong on both ends. That is OM-02's territory,
   not this one.
