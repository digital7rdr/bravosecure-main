# OM-01 — 1:1 and reaction outbox rows carry no SN-06 cert metadata, so a long-queued row ships a dead cert behind a "sent" tick

## Verdict

**CONFIRMED.** The SN-06 fix landed only on the group fan-out enqueue; the 1:1 and reaction
enqueue sites still write cert-less payloads, and the drain therefore ships them verbatim.

- `src/modules/messenger/runtime/productionRuntime.ts:2873` (1:1 send) —
  `payload:      JSON.stringify({outerSealed, expiresAtSec}),` — no `certExpSec`, no re-seal inputs.
- `src/modules/messenger/runtime/productionRuntime.ts:3338` (reaction fan-out) —
  `payload:      JSON.stringify({outerSealed}),` — same gap.
- `src/modules/messenger/runtime/productionRuntime.ts:2619-2626` (group) is complete:
  `payload: JSON.stringify({outerSealed, expiresAtSec, certExpSec, sealedBody, attachment, groupId, kind, clientMsgId})`.
- `src/modules/messenger/runtime/outboxCertFreshness.ts:37` —
  `if (certExpSec === undefined) {return false;}` → a cert-less payload is always classified "fresh",
  so `drainOutbox` takes the `outerSealed = payload.outerSealed;` branch at
  `productionRuntime.ts:7467` and re-ships bytes minted hours ago.
- Cert lifetime is 1h: `apps/auth-service/src/sender-cert/sender-cert.service.ts:95` —
  `const ttlSec = this.config.get<number>('senderCert.ttlSeconds') ?? 3600;`
  Receiver tolerance is 120s: `packages/messenger-core/src/crypto/senderCert.ts:115-117` —
  `const tolerance = params.clockToleranceSec ?? 120; ... if (claims.exp + tolerance < now) {throw new CryptoError('sender cert expired');}`
- The loss is silent, exactly as claimed: cert pre-verify failure ack-destroys the envelope
  (`productionRuntime.ts:5546` — `await deps.relay.ack(frame.data.envelopeId, frame.data.ackToken, 'discarded');`),
  and the honest receipt only reaches a submitter the relay knows —
  `apps/messenger-service/src/relay/envelope.service.ts:229-234`: _"The WS gateway passes a submitter
  address; the HTTP controller does not"_ + `:381` `this.hub.emitToDevice(submitter, 'envelope.undeliverable', ...)`.
  The drain always uses HTTP (`relay.send` at `productionRuntime.ts:7476`), so no submitter mapping
  exists → no `envelope.undeliverable` → the B-46 auto-resend at `productionRuntime.ts:827` never
  fires, and the bubble stays at `'sent'` (set at `:7485`) forever.

Note: the AAD staleness bound is **not** the problem — `SEALED_AAD_MAX_AGE_MS = 30 * 24 * 60 * 60 * 1000`
(`packages/messenger-core/src/crypto/sealedSender.ts:373`). The cert is the only thing that ages out.

## Mechanism

1. User sends a 1:1 message (or taps a reaction) while offline / on a half-dead socket.
   `sendText` seals with `cert = await certCache.get()` (`:2800`) and writes an outbox row whose
   payload is `{outerSealed, expiresAtSec}` (`:2867-2874`). `sendReaction` writes `{outerSealed}` (`:3332-3339`).
2. No `envelope.accepted` arrives, so `markDelivered` never runs; the row survives with
   `status='pending'`. SN-04 (`sqlOutboxStore.ts:235`) deliberately keeps offline rows out of the
   `failed` bucket, so the row can sit for hours/days — that is the intended design.
3. > 1h later connectivity returns and `drainOutbox` runs. `isStoredCertStale(undefined)` returns
   > `false` (`outboxCertFreshness.ts:37`), so the drain ships the **original** `outerSealed` —
   > whose embedded sender cert expired ~1h after compose — over HTTP.
4. The relay accepts it (200, `wakeEligible`), the drain flips the bubble to `'sent'`
   (`:7485`) and deletes the row (`:7500`).
5. The recipient's `handleDeliver` runs `verifySenderCert` **before** libsignal decrypt
   (`:5479`), gets `sender cert expired`, and acks `disposition: 'discarded'` (`:5546`) —
   hard-deleting the envelope from the relay.
6. `EnvelopeService.ack` looks up `takeSubmitter(envelopeId)`; the HTTP submit stored none, so the
   `envelope.undeliverable` emit is skipped entirely. The sender's ratchet already advanced, the
   plaintext is gone from the outbox, and the UI shows a delivered tick for a message nobody has.
   For a reaction there is not even a bubble to be suspicious about — the chip just never appears
   on the peer's device.

## Fix

Mirror the shipped group SN-06 fix at the two remaining enqueue sites, and teach the single
re-seal callback the two extra shapes. **No wire change, no server change, no DB migration** —
`payload` is an opaque `TEXT` JSON blob (`src/modules/messenger/crypto/db.ts:204-216`), so new JSON
keys are additive; rows written by older builds simply lack them and keep the current behaviour.

```ts
export function isStoredCertStale(
  certExpSec: number | undefined,
  nowMs: number = Date.now(),
): boolean {
  if (certExpSec === undefined) {
    return false;
  }
  const nowSec = Math.floor(nowMs / 1000);
  return certExpSec - nowSec <= OUTBOX_CERT_RESEAL_MARGIN_SEC;
}
```

Append:

```ts
/** Which send shape a stored outbox payload can be re-minted as, if any. */
export type OutboxResealKind = 'group' | 'direct' | 'reaction';

/**
 * SN-06 / OM-01 — classify a stored payload by the inputs it carries.
 *
 * Order matters: a GROUP reaction row carries `groupId` too, and it must be
 * re-sealed as a reaction (empty body + `reaction` directive), not as a group
 * text post. Legacy group rows written before OM-01 carry `groupId` +
 * `sealedBody` and keep classifying as 'group', so an in-flight queue survives
 * the upgrade unchanged. `undefined` means "nothing to re-mint from".
 */
export function outboxResealKind(payload: {
  groupId?: string;
  sealedBody?: string;
  reaction?: unknown;
}): OutboxResealKind | undefined {
  if (payload.reaction) {
    return 'reaction';
  }
  if (payload.sealedBody === undefined) {
    return undefined;
  }
  return payload.groupId === undefined ? 'direct' : 'group';
}
```

### Back-compat

- **Wire:** unchanged. `relay.send` payload, envelope shape, AAD block and sender-cert verification
  are untouched. Server needs no deploy; old and new clients interoperate identically.
- **Local rows written by an older build:** lack `certExpSec` → `isStoredCertStale(undefined) === false`
  → unchanged ship-stored-bytes path (`outboxCertFreshness.ts:29-32` documents exactly this).
- **Local group rows written by the current build:** unchanged — `outboxResealKind` still returns
  `'group'` for `{groupId, sealedBody}`.
- **Downgrade (new row read by an older build):** the older `drainOutbox` reads only
  `outerSealed`/`expiresAtSec`/`certExpSec`/`sealedBody`/`groupId`; the extra `reaction`/`replyTo`
  keys are ignored. A 1:1 row would hit the old guard `payload.groupId === undefined` and throw
  `outbox_cert_expired_unresealable` → recordAttempt/backoff, no data loss (the row survives).
- **DB:** no `SCHEMA_VERSION` bump (currently 14, `crypto/db.ts:54`). `payload` is TEXT JSON.

## Risk

- **The re-seal keeps the original `clientMsgId`, and the relay dedups on
  `(recipient, clientMsgId)`** (`apps/messenger-service/src/relay/envelope.service.ts:157-183`,
  `claimClientMsgId`). So in the narrow _lost-ack_ case — relay accepted the original but the
  `envelope.accepted` never reached us — the re-minted fresh-cert envelope is discarded by the
  dedup and the recipient still holds the dead one. This is a **pre-existing property of the
  shipped group SN-06 fix**, not something introduced here, and the dominant case (never accepted
  at all, hence the surviving row) is fully fixed. Minting a new `clientMsgId` is what B-46 does
  (`productionRuntime.ts:821-823`) but only because it _knows_ the envelope was destroyed; doing it
  blindly here risks double delivery. Leave as-is; log it as a follow-up.
- **Plaintext at rest.** The 1:1 payload now stores `sealedBody: text` and the attachment's per-file
  AES key. Both already live in the same SQLCipher DB (`messages.content`, `messages.media_key`),
  and the group path already stores a plaintext `sealedBody` when no master key exists
  (`productionRuntime.ts:2478-2480`). No new exposure class — but a reviewer should confirm no log
  statement ever prints `row.payload` (the log-audit gate covers `console.*`; the two existing
  outbox warns print ids only).
- **AAD is re-stamped with `Date.now()` at re-seal.** Intentional and identical to the shipped
  group behaviour; the receiver's stale bound is 30 days so this is not load-bearing, but it does
  mean the displayed order can differ from compose order (that is OM-02/OM-05 territory — do not
  "fix" it here by reusing the compose timestamp without architecture sign-off).
- **The reaction AAD stays `{to, ts}` only.** It looks under-specified next to the text paths, but
  widening it changes what the receiver verifies (`verifySealedAad` extended fields are checked
  only when both sides carry them) — out of scope for OM-01 and a stop-condition ("AAD binding").
- **`outboxResealKind` ordering is the whole correctness of the routing.** Reaction before group is
  deliberate; flip it and every group reaction re-ships as an empty group text post.
- **`getIssued()` swap.** Verify the imported `SenderCertCache` is the messenger-core one
  (`productionRuntime.ts:52`, `packages/messenger-core/src/runtime/certCache.ts:57`) — the
  legacy `src/modules/messenger/runtime/certCache.ts` copy has **no** `getIssued` and would fail to
  compile if it were the one in play.
