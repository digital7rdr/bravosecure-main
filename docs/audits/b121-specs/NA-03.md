# NA-03 - Cold-start notification routing is serialized behind unbounded push-register network I/O

## Verdict

**CONFIRMED** (mechanism exactly as described; the audit's "20-40 s" understates it — the worst case
is _unbounded_).

Evidence from the current tree (`src/modules/messenger/push/fcmBootstrap.ts`, 1631 lines):

- `startFcmBootstrap` awaits the token fetch at **:218** — `const token = await messaging().getToken();`
  — with no deadline of any kind.
- It then awaits both registers at **:226-229** —
  `const results = await Promise.all([ registerDataToken(token)…, registerVoipToken(token)… ]);`
- Both land in `registerToken`, whose HTTP call at **:1338** is a bare `fetch`:
  `const res = await fetch(\`${MSG_BASE_URL}/push/${endpoint}\`, {method: 'POST', headers, body: …});`— no`signal`, no `AbortController`. And it can run **twice** per endpoint (401 → `refreshAccessTokenShared()`→`return attempt(true);` at **:1343-1346**), each unbounded, plus the refresh round-trips themselves.
- Only **after** all of that does **:266** `installNotifeeHandlers();` run, and that function is the
  _sole_ owner of cold-launch routing: **:1234** `const initial = await notifee.getInitialNotification();`
  → synthetic `EventType.PRESS` → `handle(...)` → `navigate('Main', {screen:'MessengerTab', params:{screen:'CallScreen'…}})`
  (**:1199-1214**). Repo-wide grep: `getInitialNotification` appears **only** in this file.
- The unboundedness is the project's own documented RN behaviour:
  `packages/messenger-core/src/transport/fetchWithTimeout.ts:3-6` — _"React Native's Android stack (OkHttp)
  is configured with no read timeout, so a black-holed connection … leaves `fetch` pending for minutes
  rather than failing."_ That is the SN-01 fix the audit points at, and `/push/register*` was never wrapped.
- The block is also ahead of `installCallKitEventHandlers()` (**:335**, Telecom/system-UI **Answer** route)
  and `drainPendingActions()` (**:341**, the killed-app queued reply/read/decline flush), so the same stall
  delays _three_ user-visible paths, not one.
- The in-code justification at **:263-265** ("The handler is attached after token registration so ready
  calls arriving immediately after install don't race the navigation ref bootstrap") is **stale/incorrect**:
  the handler already owns that race internally — `waitReady(20000)` at **:1140-1156** for calls and an
  8 s `navigationRef.isReady()` poll at **:996-1000** for msg-wake. Nothing in the handler needs the FCM
  token or a completed server register.

## Mechanism

1. Device is killed / process dead. A `voip-wake` arrives; the module-scope
   `messaging().setBackgroundMessageHandler` (**:1400**) draws the ring via notifee + Telecom.
2. User taps **Answer**. The slim bundle-entry notifee handler
   (`callNotification.ts:500-566`, registered from `index.js`) handles `decline-`/`reply-`/`read-` only —
   for an accept it just `dismissCallNotif(callId)` and lets the pressAction's `launchActivity` cold-start
   the app. The route to `CallScreen` is _entirely_ on `getInitialNotification()`.
3. Cold start runs: `MainNavigator` gates on `user?.id`, computes `ownerKey`, calls
   `configureMessengerRuntime`, then inside `InteractionManager.runAfterInteractions` fires
   `void startFcmBootstrap()` (`src/navigation/MainNavigator.tsx:455,480-482`).
4. `startFcmBootstrap` runs the permission/channel block, then **blocks** on
   `await messaging().getToken()` (**:218**). On a degraded link FCM's own network registration can hang
   for tens of seconds.
5. It then **blocks** on `await Promise.all([registerDataToken, registerVoipToken])` (**:226-229**).
   Each goes through `registerToken` → bare `fetch` (**:1338**). If the TCP connection establishes and
   then black-holes (2G handover, NAT rebind, captive Wi-Fi with dead upstream), OkHttp's zero read
   timeout means the promise never settles. A 401 doubles it.
6. `installNotifeeHandlers()` (**:266**) never runs → `getInitialNotification()` never runs →
   `CallScreen` never mounts. The Telecom Answer route (**:335**) and the pending-action drain (**:341**)
   are stuck behind the same await.
7. Caller's 45 s ring expires. Callee sees the app open on Home (or, if routing finally lands after the
   offer window closed, the NA-02 "Answering…" dead-end). Symptom reported as "I tapped Answer and
   nothing happened."

Nothing below the register block consumes its result: `onTokenRefresh` (**:249**), `installNotifeeHandlers`
(**:266**), `onMessage` (**:277**), `setupCallKit`/`startVoipPushBootstrap`/`installCallKitEventHandlers`
(**:333-335**) and `drainPendingActions` (**:341**) are all independent of it. The serialization is
incidental, not a dependency.

## Fix

Four edits, all in `src/modules/messenger/push/fcmBootstrap.ts` (+1 new test file). No wire-format change,
no schema change, no server change, no security-check change.

**Replacement:**

```ts
// NA-03 — getToken() has no abort hook and blocks on FCM's own network
// registration, so a dribbling link stalls it without bound. Race it, and bound
// the two POSTs (F1). A miss is not fatal: serverRegistered stays false and
// ensurePushRegistered re-asserts on the next WS `connected`.
async function doRegisterPushTokens(): Promise<void> {
  try {
    let timer: ReturnType<typeof setTimeout> | undefined;
    const token = await Promise.race<string | null>([
      messaging().getToken(),
      new Promise<null>(resolve => {
        timer = setTimeout(() => resolve(null), GET_TOKEN_TIMEOUT_MS);
      }),
    ]).finally(() => {
      if (timer) {
        clearTimeout(timer);
      }
    });
    if (!token) {
      console.warn('[fcm] getToken empty or timed out — will retry on next WS connect');
      return;
    }
    console.log('[fcm] getToken ok, len =', token.length, 'prefix =', token.slice(0, 10) + '…');
    // Register against BOTH endpoints. /register-voip wakes the device for
    // incoming calls; /register is for chat-message wakes. They share the same
    // FCM token but live in different Redis keyspaces on the server so we can
    // lifecycle them independently.
    const results = await Promise.all([
      registerDataToken(token)
        .then(() => true)
        .catch(e => {
          console.warn('[fcm] register-data failed:', (e as Error).message);
          return false;
        }),
      registerVoipToken(token)
        .then(() => true)
        .catch(e => {
          console.warn('[fcm] register-voip failed:', (e as Error).message);
          return false;
        }),
    ]);
    // Both must succeed to flip the gate — partial success would leave either
    // chat-wake or call-wake broken.
    if (results.every(Boolean)) {
      serverRegistered = true;
      console.log('[fcm] server-register OK (both endpoints)');
    } else {
      console.warn('[fcm] server-register PARTIAL — next attempt will retry');
    }
  } catch (e) {
    console.warn('[fcm] push register failed:', (e as Error).message);
  }
}

let registerInFlight: Promise<void> | null = null;
async function registerPushTokens(): Promise<void> {
  // Why: bootstrap now fires this without awaiting, so a re-login or a WS
  // `connected` landing mid-flight must join the existing attempt instead of
  // firing a second pair of POSTs.
  if (registerInFlight) {
    return registerInFlight;
  }
  registerInFlight = doRegisterPushTokens();
  try {
    await registerInFlight;
  } finally {
    registerInFlight = null;
  }
}
```

### F4 (rider, required to avoid a self-inflicted regression) — durable decline in the rich handler

notifee's `onBackgroundEvent` is **last-wins**, so F3 makes the rich handler replace the slim
bundle-entry one (`callNotification.ts:500`) ~20-40 s earlier in the process's life. In that widened
window a **Decline** tap takes the rich branch, which on a not-yet-connected WS only logs
`'[notifee] decline → no live transport, falling through to no-answer'` (**:1091**) — whereas the slim
handler enqueues a durable pending-decline (`callNotification.ts:549-559`) that
`drainPendingActions` flushes. Close the gap with the existing helper.

**Schema / migration:** none. No SQLCipher or outbox schema is touched; `pendingActions` uses its
existing AsyncStorage queue and its existing `PendingDecline` shape.

**Wire format / back-compat:** none. The same `POST /push/register` and `POST /push/register-voip`
requests with the same headers and the same `{platform, token}` body are sent; only the client-side
deadline changes. Old and new clients are indistinguishable to `messenger-service`. No server deploy
ordering constraint.

**Security constraints:** no check is added, removed, weakened, or dev-branched. No encryption
primitive, envelope shape, AAD binding, sender-cert path, dwell semantic, or vault-MFA gate is touched.
The `voipWakeVerify` HMAC gate on the ring path (**:1423-1436**) is untouched. The one log line that
touches the FCM token is carried over **byte-identical** (`'prefix =', token.slice(0, 10) + '…'`) so the
log-audit surface is unchanged.

## Blast radius

**Files edited**

- `src/modules/messenger/push/fcmBootstrap.ts` — the only production file.
- `src/modules/messenger/__tests__/fcmBootstrapOrder.test.ts` — new.

**Functions changed**

- `startFcmBootstrap` (exported; sole caller `src/navigation/MainNavigator.tsx:480-482`, called as
  `void startFcmBootstrap().catch(...)` — it already ignores the resolution, so making it resolve
  sooner changes nothing for the caller).
- `retryServerRegister` → replaced by `doRegisterPushTokens` + `registerPushTokens`. Both former call
  sites updated (`ensurePushRegistered:79`, `startFcmBootstrap:154`). `retryServerRegister` is
  module-private — repo-wide grep confirms no external reference.
- `ensurePushRegistered` (exported; one external caller,
  `src/modules/messenger/runtime/productionRuntime.ts:1161-1163`, `void ensurePushRegistered().catch(...)`
  on every WS `connected`) — behaviour identical, now joins an in-flight attempt instead of racing one.
- `registerToken` (module-private; called by `registerDataToken` / `registerVoipToken` only).
- `installNotifeeHandlers` — moved, not modified (except F4's decline branch).

**Behaviour deltas a reviewer should expect**

1. `startFcmBootstrap()` now resolves without waiting for the network. Nothing awaits its resolution.
2. The rich notifee background handler replaces the slim one earlier in process life (F4 covers the
   one real gap that opens).
3. On a hard-down network the device may finish boot **unregistered** for push, where before it would
   eventually register after a long hang. Self-heals via `ensurePushRegistered` on the next WS
   `connected` (60 s throttle, `ENSURE_REGISTER_MIN_INTERVAL_MS`) and on the next `startFcmBootstrap`
   (`serverRegistered` still `false` → the `if (started)` retry branch).
4. `serverRegistered` can now flip **after** `startFcmBootstrap` resolves. It is already mutated from a
   floating promise in the `onTokenRefresh` callback (**:255-257**), so this is not a new shape.

**Overlapping findings**

- **NA-04** edits `installCallKitEventHandlers`'s `onAnswer` in this same file (**:379-399**) — same
  file, disjoint function. Land them in either order; expect a trivial context-only merge.
- **NA-01** edits `incomingCallCache.setIncomingCallPayload` (different file); its `fcmBootstrap.ts:1493`
  call site is untouched here.
- **NA-02** (dead-offer terminal state in `useCall`/`CallScreen`) is downstream — NA-03 shrinks the
  window that feeds it but does not fix it.
- **SN-01** already owns `fetchWithTimeout`; this reuses it, adds nothing to `messenger-core`.

**What could regress**

- Metro/Babel resolution of the `@bravo/messenger-core/transport/fetchWithTimeout` **subpath** (first
  such subpath import in the runtime tree — see the fallback in F1).
- A too-aggressive `PUSH_REGISTER_TIMEOUT_MS` on a genuinely slow-but-working link → transiently
  unregistered device. Mitigated by the WS-connect re-assert; 10 s is 2.5× the 4 s precedent already
  shipped in `unregisterPush.ts`.
- `Promise.race` on `messaging().getToken()` leaks nothing (timer cleared in `.finally`), but the losing
  `getToken()` promise still settles later and is intentionally discarded.

## Risk

- **The `installNotifeeHandlers` hoist is the whole fix — verify it is genuinely dependency-free.**
  The reviewer should independently confirm the handler never reads the FCM token, `serverRegistered`,
  or a notifee channel. It doesn't (channels are only needed to _display_, and this handler only
  dismisses + navigates), but the comment being deleted at **:263-265** explicitly claims a nav-ref race
  that must be re-checked against `waitReady(20000)` (**:1140-1156**) and the 8 s msg-wake poll
  (**:996-1000**).
- **Handler last-wins semantics.** `notifee.onBackgroundEvent` is a single setter, not an emitter. F3
  moves the moment the rich handler displaces the slim one. F4 is the mitigation; if F4 is dropped, the
  widened window is a real (small) behaviour regression for killed-app declines during warm boot.
- **Fire-and-forget register.** Be suspicious of "the device silently never registers". The self-heal
  chain is `productionRuntime.ts:1161` → `ensurePushRegistered` on every WS `connected`, throttled 60 s.
  If that call site is ever removed, NA-03's fix converts a slow register into a _missing_ one. Worth a
  comment reference in the diff.
- **Timeout tuning is a judgement call**, not a derived constant. 10 s for both `getToken` and the POSTs
  is chosen against the 4 s in `unregisterPush.ts` and the 20 s `TRANSPORT_TIMEOUT_MS`. If field logs
  show `getToken empty or timed out` at any meaningful rate on healthy devices, raise
  `GET_TOKEN_TIMEOUT_MS` before touching anything else.
- **Subpath import.** First runtime `@bravo/messenger-core/<path>` import in `src/`. tsconfig, babel
  alias and the jest mapper all provision it, but Metro resolution is only proven by an actual app boot —
  do not merge on unit tests alone.
- **Not fixed by this change:** once routing lands, NA-02's dead-offer "Answering…" dead-end is still
  reachable if the cold start outran the 45 s offer window. NA-03 shrinks the exposure; it does not
  close it.
