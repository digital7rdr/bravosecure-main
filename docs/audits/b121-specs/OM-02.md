# OM-02 - Clamp the inbound transcript ordering timestamp to the relay's server timestamp (display-only)

## Verdict

**CONFIRMED-WITH-DRIFT** — the defect is exactly as described; only the audit's bare filenames and
line numbers drift (there is no `aad.ts` file — the AAD windows live in
`packages/messenger-core/src/crypto/sealedSender.ts`).

Evidence from the current tree:

1. `packages/messenger-core/src/crypto/sealedSender.ts:347` —
   `export const SEALED_AAD_FUTURE_MS = 24 * 60 * 60 * 1000;` and `:373`
   `export const SEALED_AAD_MAX_AGE_MS = 30 * 24 * 60 * 60 * 1000;`, enforced at `:499-500`
   `if (aad.ts < now - maxAge) {return {ok: false, reason: 'stale'};}` /
   `if (aad.ts > now + futureMs) {return {ok: false, reason: 'future'};}`. A sender 23h fast is
   **accepted**.
2. `src/modules/messenger/runtime/productionRuntime.ts:7293` (1:1) and `:7232` (group text) —
   `created_at: new Date(typeof unwrapped.aad?.ts === 'number' ? unwrapped.aad.ts : Date.now()).toISOString(),`
   i.e. the sender's wall clock, verbatim, with **no** reference to the server timestamp.
3. `src/modules/messenger/runtime/productionRuntime.ts:6204-6206` (stashed group drain,
   `replayGroupSealedDecode`) — same pattern via
   `const sentTs = (sealed.aad as {ts?: number} | undefined)?.ts;`.
4. Own messages use the **local** clock: `productionRuntime.ts:2385` `const sentAt = new Date().toISOString();`
   consumed at `:2441` `created_at: sentAt,` (and `:2781`). So the two ends of one thread are keyed
   on two different clocks.
5. Ordering is strictly `created_at`: `src/modules/messenger/store/messengerStore.ts:555-565` —
   `if (tail && msg.created_at < tail.created_at) { ... binary splice ... } else { list.push(msg); }`
   plus the comparator at `:77` `if (a.created_at !== b.created_at) {return a.created_at < b.created_at ? -1 : 1;}`
   and ChatScreen's merge sort at `src/screens/messenger/ChatScreen.tsx:270`.
6. The server timestamp **is already on the wire and already typed on the client**, unused:
   `apps/messenger-service/src/relay/envelope.service.ts:195` `timestamp: now,` →
   `envelope.service.ts:581` (`tryFanOut`) and `apps/messenger-service/src/gateway/messenger.gateway.ts:735-738`
   (`flushPendingOnConnect`) both emit `timestamp: env.timestamp`, and
   `src/modules/messenger/transport/protocol.ts:239-246` declares `ServerEnvelopeDeliver.data.timestamp: number`.
   `handleDeliverInner` reads `frame.data.envelopeId` / `frame.data.ackToken` but **never**
   `frame.data.timestamp`.

Nothing in the tree clamps, compares, or even reads the server timestamp on the receive path.

## Mechanism

1. Peer B's device clock is fast by Δ (NTP off, manual clock, wrong timezone-as-clock). Δ can be
   minutes (typical) up to just under 24h (still accepted).
2. B sends. `sealPayload` stamps `aad: {to, ts: Date.now(), ...}` (`productionRuntime.ts:2822-2827`
   for 1:1, `:2543-2549` for group) — `ts = trueNow + Δ`.
3. The relay accepts and stamps its own `timestamp = now` (`envelope.service.ts:195`) — the true
   time. Both values ride to A: the ciphertext-bound `aad.ts` and the plaintext `timestamp`.
4. A's `verifySealedAad` passes: `aad.ts > now + futureMs` is false because `futureMs` is 24h
   (`sealedSender.ts:500`). This is deliberate (MEDIUM-1: a tight future bound was silently
   destroying messages) and must stay.
5. A builds the row with `created_at = aad.ts` (`productionRuntime.ts:7293`), i.e. Δ in the future,
   and persists it (`store.appendMessage` + `sqlMessages.upsert`).
6. A replies. A's own row uses A's local clock (`productionRuntime.ts:2385`), so
   `created_at ≈ trueNow < tail.created_at (= trueNow + Δ)`. `appendMessage` takes the
   out-of-order branch at `messengerStore.ts:555` and **binary-splices the reply above B's
   question**. Every subsequent message from either side, for the next Δ of wall time, splices
   above B's message too.
7. The mis-ordering is durable: it is written into SQLite, into the backup mirror
   (`backupWireV3.ts:73` `msg_created_at: msg.created_at`), and re-derived identically on rehydrate
   (`sqlMessageStore.ts:189` `ORDER BY conversation_id, created_at ASC, id ASC`). It also regresses
   the chat-list ordering (`messengerStore.ts:1162` `Date.parse(cur.created_at) <= Date.parse(newest.created_at)`).

The mirror case (slow clock) exists too but is bounded differently and is **not** clamped by this
fix — see "Fix / why the audit's symmetric clamp is wrong" below.

## Fix

Display-only. Zero wire change (the field already exists and is already sent by every deploy),
zero schema change, zero crypto change. `packages/messenger-core/**` is **not** touched.

### F1 — new file `src/modules/messenger/runtime/orderingClock.ts`

Sibling of `outboxCertFreshness.ts` / `certCache.ts`: a tiny pure module with no native or runtime
imports, so it unit-tests without booting the messenger runtime (same rationale documented at
`outboxCertFreshness.ts:5-8`).

```ts
/**
 * OM-02 — ordering timestamp for an inbound message row.
 *
 * The transcript sorts strictly on `created_at` (messengerStore.appendMessage
 * binary-splices on it) and inbound rows take that value from the SENDER's wall
 * clock (`aad.ts`). `verifySealedAad` deliberately accepts up to 24h of future
 * skew (SEALED_AAD_FUTURE_MS, audit MEDIUM-1) so a mis-set clock cannot destroy
 * messages — which leaves a fast-clocked peer able to pin its rows at the bottom
 * of the thread while every later reply splices ABOVE the question.
 *
 * This module is DISPLAY-ONLY. Its output feeds `LocalMessage.created_at` and
 * nothing else: never `verifySealedAad`, never the seen-envelope set, never
 * `expires_at`. The AAD accept windows in
 * `packages/messenger-core/src/crypto/sealedSender.ts` are untouched.
 */

/**
 * Tolerance before the sender's stamp is treated as impossible rather than
 * merely imprecise. Covers seal→submit latency (a couple of RTTs) plus ordinary
 * NTP jitter; anything beyond it is a mis-set clock, not a slow network.
 */
export const ORDERING_FUTURE_SKEW_MS = 2 * 60 * 1000;

/**
 * `refTsMs` must be an UPPER BOUND on when the message can have existed — the
 * relay's accept time (`ServerEnvelopeDeliver.data.timestamp` /
 * `RelayEnvelope.timestamp`) on the live paths, or our own receive time for a
 * stashed row drained later.
 */
export function orderingTsMs(aadTsMs: number | undefined, refTsMs: number | undefined): number {
  const ref =
    typeof refTsMs === 'number' && Number.isFinite(refTsMs) && refTsMs > 0 ? refTsMs : Date.now();
  if (typeof aadTsMs !== 'number' || !Number.isFinite(aadTsMs) || aadTsMs <= 0) {
    return ref;
  }
  // Why: the reference bounds the FUTURE only. A store-and-forwarded or
  // outbox-queued envelope is legitimately much OLDER than the reference
  // (MSG-01 / L18) and must keep its send time or the drain ordering fixes
  // those audits shipped are undone.
  return aadTsMs > ref + ORDERING_FUTURE_SKEW_MS ? ref : aadTsMs;
}

export function orderingCreatedAt(
  aadTsMs: number | undefined,
  refTsMs: number | undefined,
): string {
  return new Date(orderingTsMs(aadTsMs, refTsMs)).toISOString();
}
```

**Why future-only, i.e. why the audit's literal `|aad.ts − serverTs| > skew` is wrong.**
`serverTs` is the relay _accept_ time, not the delivery time. A message composed offline and
drained hours later from `SqlOutboxStore` (backoff up to 5 min/attempt, `sqlOutboxStore.ts:56-60`,
rows survive across launches) legitimately has `aad.ts ≪ serverTs`; a stashed group envelope
drained after its rekey arrives can be up to 30 days older than the drain reference
(`pendingGroupEnvelopeStore.ts` `RETENTION_MS = 30 * 24 * 60 * 60 * 1000`). A symmetric clamp would
force both classes to the arrival instant and **undo audit MSG-01 and L18
GROUP-DRAIN-RECEIVE-TIME-ORDERING** — the fixes whose comments sit on the exact lines we are
editing (`productionRuntime.ts:7228-7231`, `:6198-6203`, `messengerStore.ts:548-553`). Only the
future direction is physically impossible and therefore clampable.

### Wire / schema / back-compat

- **No wire change.** `timestamp` is already emitted by every server code path
  (`envelope.service.ts:581`, `messenger.gateway.ts:738`, HTTP `GET /envelopes` returns full
  `StoredEnvelope`) and already declared on the mobile `ServerEnvelopeDeliver`
  (`src/modules/messenger/transport/protocol.ts:242`) and `RelayEnvelope`
  (`packages/messenger-core/src/transport/relayClient.ts:30`). An old server → new client is
  impossible to hit (the field predates the current deploy), but the helper's
  `refTsMs` fallback makes a missing/zero value degrade to today's behaviour anyway.
- **No SQLCipher schema bump.** `messages.created_at` already exists; `pending_group_envelopes`
  already carries `received_at_ms`.
- **No backfill.** Existing rows keep their stored `created_at`. Rewriting them would change
  `msg_created_at` in the Merkle leaf (`backupMerkle.ts:65`, `:127-141`) for already-committed
  rows and manufacture exactly the `root_mismatch` drift `BACKUP_LOOP.md` §2 exists to prevent.
  New rows are clamped once, before `store.appendMessage` **and** `sqlMessages.upsert`, so store,
  SQLite and the mirror all agree from birth.

## Risk

Things a reviewer should be suspicious of, in order:

1. **Did anything under `packages/messenger-core/` change?** It must not. `git diff --stat
packages/messenger-core` must be empty. `SEALED_AAD_FUTURE_MS` / `SEALED_AAD_MAX_AGE_MS` /
   `verifySealedAad` are stop-condition code (CLAUDE.md "Never weaken transitions"); the fix is
   valid _because_ it lives entirely in the store/render layer. Test assertion 10 exists to catch a
   drive-by narrowing.
2. **`serverTsMs` is relay-controlled and unauthenticated.** It must never reach a crypto or
   retention decision — not `verifySealedAad`, not `seenEnvelopes`, not `expires_at`
   (which stays `expiresAtSec * 1000`, sender-derived, per `MESSENGER_BACKEND.md:190`). Grep the
   diff: the only consumer of the new parameter should be `orderingCreatedAt`. The residual power a
   hostile relay gains is the ability to nudge a row's _display_ slot — strictly less than the
   reordering it already achieves by delaying delivery.
3. **Is the clamp applied exactly once, at row construction?** If a later change moves it to render
   time, the Zustand store, the SQLite row and the backup Merkle leaf diverge and the
   `root_mismatch` class re-opens. All three writes (`appendMessage`, `sqlMessages.upsert`, mirror)
   must see the same string.
4. **No backfill / no migration.** Any UPDATE over existing `messages.created_at` re-hashes
   already-committed Merkle leaves. Confirm the diff contains no SQL.
5. **Asymmetry is deliberate, not an oversight.** The audit text says `|aad.ts − serverTs|`; this
   spec clamps the future side only. A reviewer who "completes" the symmetry will silently revert
   MSG-01 and L18. The slow-clock mirror case is left unfixed on purpose — fixing it needs a
   _lower_ bound reference that does not exist on the wire (the relay's accept time is an upper
   bound only). If it becomes a real complaint, the correct follow-up is a per-peer clock-offset
   estimate (median of `serverTs − aad.ts` over recent envelopes) applied as a display offset, not a
   tighter clamp.
6. **Disappearing-message TTL recompute drifts slightly for clamped rows.**
   `ChatScreen.tsx:725` recomputes a reship TTL as `expires_at - created_at`. `expires_at` is still
   sender-derived, so clamping `created_at` down inflates that recomputed TTL by the skew. Pre-existing
   in kind (a skewed sender's burn deadline was already wrong); bounded by the skew; display/reship
   only, never the actual burn (which uses `expires_at` directly). Worth a follow-up note, not a
   blocker.
7. **Positional-argument creep.** `handleIncoming` reaches 15 positional parameters. A module-level
   `Map<envelopeId, serverTs>` was considered and rejected (lifecycle/leak risk across the WS + HTTP
   drain + archive-replay entry points, all of which already share `inFlightEnvelopes`). If the
   parameter list is refactored to an options object later, that is a separate, test-covered change
   — not part of this fix (CLAUDE.md: minimal diffs, no drive-by refactors).
