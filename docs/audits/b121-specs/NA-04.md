# NA-04 - Telecom/system-UI Answer with a cached payload never surfaces the app, so CallScreen's FGS start is a background start and Android denies the mic

## Verdict

**CONFIRMED** (with one important correction to the audit's proposed fix — see §Fix).

Evidence from the current tree:

1. `src/modules/messenger/push/fcmBootstrap.ts:379-399` — `bringAppToForeground()` sits **only** inside the `if (!payload)` early-return branch:

   ```
   381:      const payload = cache.getIncomingCallPayload(callId);
   382:      if (!payload) {
   383:        console.warn('[callkit-ev] no cached payload for callId=', callId, ...);
   388:        bridge.bringAppToForeground();
   389:        return;
   390:      }
   394:      void navigateToIncomingCall(callId, payload);
   ```

   The happy path (payload present — the normal case, since `fcmBackgroundHandler` seeds the cache at `fcmBootstrap.ts:1493` _before_ `bridge.reportIncomingCall(...)` at `:1522`) navigates and never surfaces the app.

2. It is the only call site in the repo: `grep bringAppToForeground` → `callKitBridge.ts:480` (definition) and `fcmBootstrap.ts:388` (sole caller). Nothing else brings the app forward on a Telecom answer.

3. Nothing native does it either. `react-native-callkeep`'s `VoiceConnection._onAnswer` only broadcasts to JS — `node_modules/react-native-callkeep/android/src/main/java/io/wazo/callkeep/VoiceConnection.java:311` `sendCallRequestToActivity(ACTION_ANSWER_CALL, handle);` — no `startActivity`.

4. The FGS is therefore started from a backgrounded process. `src/screens/messenger/CallScreen.tsx:962-963`:

   ```
   const {startCallForegroundService} = require('@/modules/messenger/runtime/callForegroundService') ...
   startCallForegroundService({kind: isVideo ? 'video' : 'voice', peer: peerName || 'Bravo Secure'});
   ```

   and the native ladder `android/app/src/main/java/com/bravosecure/app/CallForegroundService.kt:105-123` degrades `phoneCall|microphone(|camera)` → `microphone(|camera)` → `microphone` → **typeless**, logging `startForeground degraded to typeless (no background mic/camera survival)`. A typeless FGS gets no mic ⇒ silent callee.

5. Device evidence in-tree (Bravo's own service, not only the WhatsApp lines the audit quoted):
   `bravo_call_log_20260710_112445.txt:148` and `:150` —
   `W/ActivityManager: Foreground service started from background can not have location/camera/microphone access: service com.bravosecure.app/.CallForegroundService`
   preceded at `:146` by `Background started FGS: Allowed [callingPackage: com.bravosecure.app; ... uidState: SVC`.

6. The parallel notifee lane is **not** affected, which is why this only bites the system-UI/lock-screen answer: the notifee Answer action carries `pressAction: {id: acceptId, launchActivity: 'default'}` (`src/modules/messenger/push/callNotification.ts:430`), and that launch intent carries notifee's `notification`/`data` bundle, which `MainActivity.isCallLaunch` recognises (`MainActivity.kt:67-80`).

Drift note: the manifest **already** declares `android:foregroundServiceType="phoneCall|microphone|camera"` (`AndroidManifest.xml:157`) and `FOREGROUND_SERVICE_PHONE_CALL` + `MANAGE_OWN_CALLS` (`:41`, `:46`) — the B-70 fix landed after the 07-10 log above. So the _current_ build does lean on the `phoneCall` exemption exactly as the audit states; NA-04 is the missing second leg, not a re-report of B-70.

## Mechanism

1. Caller rings. `fcmBackgroundHandler` (killed/background) caches the payload (`fcmBootstrap.ts:1493`), then fires **both** ringers: `bridge.reportIncomingCall(...)` (Telecom self-managed system UI, `:1522`) and `showIncomingCallNotif(...)` (notifee, `:1525`). Warm/foreground offers take the same shape from `MainNavigator.tsx:539-552`.
2. Phone is locked (or app merely backgrounded). The user answers on the **Telecom** surface — lock-screen call UI, Bluetooth headset button, Android Auto — not the notifee button.
3. Telecom → `VoiceConnection._onAnswer` → JS `answerCall` event → `subscribeToCallKitEvents` (`callKitBridge.ts:518-523`) → `onAnswer` in `installCallKitEventHandlers` (`fcmBootstrap.ts:379`).
4. `cache.getIncomingCallPayload(callId)` **hits** (step 1 seeded it) ⇒ the `bringAppToForeground()` branch is skipped ⇒ `navigateToIncomingCall(callId, payload)` runs. `navigationRef.isReady()` is already true for a warm-backgrounded app, so it navigates immediately.
5. `CallScreen` mounts **while the process is still backgrounded**. Once the accept completes and `liveCall.state` leaves `'ringing'` (`CallScreen.tsx:935`) and `permGranted === 'granted'` (`:922`), the effect calls `startCallForegroundService(...)`.
6. `BravoCallForegroundModule.start` → `ContextCompat.startForegroundService` from a `SVC`/background uid state. `CallForegroundService.goForeground` tries `phoneCall|microphone|camera`. If the Telecom `phoneCall` while-in-use exemption applies, it survives. If it does not (Telecom connection already torn down / OEM policy / Android 15+ tightening / `startForeground` throws on the typed rung), the ladder walks down to **typeless** and the call runs with no mic FGS type: Android suspends capture and the callee is silent — the audit's `can not have ... microphone access` line.
7. Independently of the mic, the user-visible defect is that the app never comes forward at all: `CallScreen` is mounted invisibly, there is no in-call UI, no mute/speaker/hang-up, and on a locked device the screen is never turned on. The only way out is the system UI.

## Fix

### Correction to the audit's proposal (read this before implementing)

The audit says "unconditional `bringAppToForeground()` at the top of `onAnswer`". Direction is right, but the _current_ implementation of `bringAppToForeground` is the wrong vehicle for the lock-screen case, and shipping it as-is would be a no-op-or-worse there:

`callKitBridge.bringAppToForeground()` calls `RNCallKeep.backToForeground()`. Its Android implementation (`node_modules/react-native-callkeep/android/src/main/java/io/wazo/callkeep/RNCallKeepModule.java:1091-1114`) takes the **`isOpened` branch** whenever a `ReactActivity` instance exists (true for a merely-backgrounded app) and starts a **bare launcher intent with only `FLAG_ACTIVITY_REORDER_TO_FRONT`** — the keyguard flags at `:1108-1110` are only applied in the `else` (fully-killed) branch.

`MainActivity` is `launchMode="singleTask"` (`AndroidManifest.xml:133`), so that intent lands in `onNewIntent` → `applyCallLaunchFlagsIfNeeded(intent)` → `isCallLaunch(intent)` is **false** (no `EXTRA_CALL_LAUNCH`, no notifee bundle) → `setCallLaunchFlags(false)` → `setShowWhenLocked(false)` + `setTurnScreenOn(false)` and **no** `requestDismissKeyguard` (`MainActivity.kt:54-102`). On a locked device the activity is reordered to front but stays behind the keyguard, is not resumed/visible, the process does not reach a foreground procstate, and the FGS start is still a background start. Net: the fix would not fix the primary case, and it would actively clear the show-over-keyguard posture.

The fix below therefore routes the bring-forward through Bravo's own launch intent, reusing the **existing** `MainActivity.EXTRA_CALL_LAUNCH` contract that the ongoing-call FGS notification already uses (`CallForegroundService.kt:144`). Four small edits, no wire format, no schema, no migration.

### 1. `android/app/src/main/java/com/bravosecure/app/BravoCallForegroundModule.kt`

Add a keyguard-aware bring-forward next to the existing `start`/`stop`. This module already owns the call-lifecycle native surface, already imports `Intent`/`Log`, and is already registered (`BravoCallForegroundPackage`).

**Anchor** (verbatim, current code):

```kotlin
  @ReactMethod
  fun stop() {
    try {
      // stopService triggers onDestroy -> stopForeground(REMOVE). Simpler and
      // free of background-start restrictions vs. delivering an ACTION_STOP.
      reactCtx.stopService(Intent(reactCtx, CallForegroundService::class.java))
    } catch (t: Throwable) {
      Log.w("BravoCallForeground", "stop failed", t)
    }
  }
```

**Insert immediately after it** (inside the class, before the closing brace):

```kotlin

  @ReactMethod
  fun bringCallUiToForeground() {
    try {
      val launch = reactCtx.packageManager.getLaunchIntentForPackage(reactCtx.packageName)
      if (launch == null) {
        Log.w("BravoCallForeground", "bringCallUiToForeground: no launch intent")
        return
      }
      launch.addFlags(
        Intent.FLAG_ACTIVITY_NEW_TASK or
          Intent.FLAG_ACTIVITY_SINGLE_TOP or
          Intent.FLAG_ACTIVITY_CLEAR_TOP,
      )
      // Why: MainActivity.isCallLaunch keys show-over-keyguard / turn-screen-on
      // off this extra. CallKeep's backToForeground() sends a BARE launcher
      // intent, which makes isCallLaunch false and CLEARS those flags, leaving a
      // lock-screen answer behind the keyguard and the process out of the
      // foreground procstate the mic/camera FGS types require.
      launch.putExtra(MainActivity.EXTRA_CALL_LAUNCH, true)
      reactCtx.startActivity(launch)
      Log.i("BravoCallForeground", "bringCallUiToForeground: launch dispatched")
    } catch (t: Throwable) {
      Log.w("BravoCallForeground", "bringCallUiToForeground failed", t)
    }
  }
```

Flags mirror the proven `CallForegroundService.buildNotification` content intent (`SINGLE_TOP or CLEAR_TOP`) plus `NEW_TASK`, which is mandatory when starting from a non-activity `Context`.

No manifest change: `SYSTEM_ALERT_WINDOW` (`AndroidManifest.xml:20`) and `MANAGE_OWN_CALLS` (`:46`) are already declared, and the answered self-managed Telecom connection is what grants the background-activity-launch window.

> `android/` is `.gitignore`d — this file must be committed with `git add -f`, same as `CallForegroundService.kt`/`MainActivity.kt` (see the NOTE headers in both). **A JS-only ship will not pick this up: an APK rebuild is required.**

/**
 * NA-04 — a system-UI (Telecom lock-screen / headset / Android Auto) Answer.
 * Exported so the accept path is testable; `installCallKitEventHandlers` wires
 * it straight onto the bridge's `onAnswer`.
 */
export function handleSystemUiAnswer(callId: string): void {
  console.log('[callkit-ev] answer callId=', callId);

  const bridge = require('./callKitBridge') as typeof import('./callKitBridge');

  const cache = require('./incomingCallCache') as typeof import('./incomingCallCache');
  // Why: NA-04 — this MUST run before we navigate, and on BOTH branches. A
  // Telecom answer leaves the process backgrounded, so CallScreen's
  // startCallForegroundService is a background FGS start and Android denies the
  // microphone/camera types ("Foreground service started from background can
  // not have ... microphone access") — CallForegroundService then degrades to a
  // typeless service and the callee is mute. It is also the only thing that
  // turns the screen on and puts the in-call controls in front of the user.
  bridge.bringAppToForeground();
  const payload = cache.getIncomingCallPayload(callId);
  if (!payload) {
    console.warn(
      '[callkit-ev] no cached payload for callId=',
      callId,
      '— Telecom event arrived without prior reportIncomingCall (notifee path may handle it)',
    );
    return;
  }
  // Same flow as the notifee Accept tap — wait for nav, then navigate to the
  // right screen. CallScreen.useCall picks up the offer SDP and runs accept
  // locally.
  //
  // Do NOT clear the cache here — the navigated screen consumes the SDP. The
  // entry clears once the call ends (peer hangup or user hangup, both routed to
  // clearByCallId through the same bridge.reportEnded path).
  void navigateToIncomingCall(callId, payload);
}

**Back-compat / wire format:** none touched. No envelope, no relay DTO, no gateway frame, no SQLCipher schema, no store migration. ### Smallest correct increment vs. follow-up

The four edits above are the whole fix and are small. Deliberately **out of scope** (propose as follow-ups, do not bundle):

- **F1 — make the FGS start wait for foreground.** `startCallForegroundService` could poll `AppState.currentState === 'active'` for up to ~1.5 s before calling `native.start`, closing the residual race between the activity launch and the accept completing. Risks delaying the FGS on a device where the launch is blocked; needs its own device soak.
- **F2 — retry the typed FGS rung after `goForeground` degraded.** `CallForegroundService.kt` currently never re-attempts the strong type once it lands typeless. A one-shot retry on the next `onStartCommand` (JS re-issues `start` on foreground) would recover a mute call. Bigger native change; separate ticket.
- **F3 — clear the keyguard posture on call end.** `setCallLaunchFlags(true)` is only cleared by a subsequent non-call launch (`MainActivity.kt:55`). Pre-existing; see §Risk.

## Risk

What a reviewer should be suspicious of, in order:

1. **Background-activity-launch (BAL) may still be denied.** Starting an activity from a background process is restricted on Android 10+. The answered self-managed Telecom connection normally grants a temporary allowlist, and `SYSTEM_ALERT_WINDOW` is declared, but neither is guaranteed on every OEM. If BAL is blocked, `reactCtx.startActivity` silently no-ops (logcat: `Background activity launch blocked`) and we are back to today's behaviour — no regression, but no fix either. **This is why the device matrix above is mandatory; do not sign this off on unit tests.** If BAL turns out to be blocked in practice, the correct escalation is a full-screen-intent `PendingIntent` (the notifee lane already proves that path works) rather than more `startActivity` flag tuning.
2. **`isCallLaunch` is now on the hot path.** The whole keyguard correctness rides on `MainActivity.EXTRA_CALL_LAUNCH` still being honoured (`MainActivity.kt:69`). A `expo prebuild --clean` regenerates a vanilla `MainActivity` and silently drops it (the file's own NOTE header warns about exactly this). Confirm the tracked `MainActivity.kt` survived the build.
3. **Keyguard posture leak (pre-existing, made more reachable).** `setCallLaunchFlags(true)` is only undone by a later non-call launch. After a lock-screen answer the activity keeps `showWhenLocked`/`turnScreenOn` until the user next opens the app from the launcher/a non-call notification. For a security product that means the app can render over the lock screen for a window after the call. It is already true for the ongoing-call FGS-notification tap; this change makes it fire on every Telecom answer. Track as follow-up F3 (clear the flags when `stopCallForegroundService` runs) — do **not** silently widen it without saying so.
4. **The `bringAppToForeground` semantics change.** It no longer early-returns when the CallKit bridge is inert. Today there is exactly one caller and it implies an active bridge, so nothing changes — but a future caller could now launch the activity on a device where Telecom was never set up. Intentional; call it out in review.
5. **Native/JS version skew.** A JS-only ship (Metro reload, OTA) against an old APK silently falls back to `backToForeground()`. That is the safe direction, but it also means a "fixed" build that was never rebuilt will still exhibit NA-04. Verify the APK, not just the bundle.
6. **The extraction is a refactor inside a bug fix.** Moving `onAnswer` into `handleSystemUiAnswer` is 15 lines with no behaviour change, justified solely to make the fix unit-testable (`installCallKitEventHandlers` is module-private and latched by `callKitHandlersInstalled`). Assertions 4/5/6 above exist to prove the move is behaviour-neutral. If a reviewer objects, the alternative is exporting `installCallKitEventHandlers` plus a test-only reset — strictly worse.
7. **Timing assumption.** The fix relies on the activity reaching a foreground state before `startCallForegroundService` fires. In practice the FGS start is gated behind accept-completion (`liveCall.state !== 'ringing'`) and the RECORD_AUDIO permission settle, which is hundreds of ms to seconds — comfortable. But it is a _race_, not a barrier. Follow-up F1 turns it into a barrier; if the device matrix shows any flakiness, do F1 before shipping.
