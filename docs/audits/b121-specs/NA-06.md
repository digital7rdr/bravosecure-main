# NA-06 - Warm-background incoming call plays two ringtones at once (in-app WAV + native device ringtone)

## Verdict

**CONFIRMED-WITH-DRIFT** — the defect reproduces exactly as described; the drift is (a) line
numbers moved a little, (b) the audit under-scopes it: the _same_ mechanism doubles the **group**
ring (`IncomingGroupCallScreen`) and doubles **vibration**, and (c) the audit's first proposed fix
(`AppState === 'active'` gate) would introduce a silent-ring regression — see §Fix.

Evidence from the current tree:

1. `src/screens/messenger/CallScreen.tsx:865-875` — the in-app ring effect is gated on `isRinging`
   only, no AppState / native-ring awareness:
   `useEffect(() => { if (!isRinging) {return;} … void tones.startRingtone(); Vibration.vibrate([0, 800, 1200, 800], true); … }, [isRinging]);`
2. `src/modules/messenger/push/callNotification.ts:448-453` — the notifee wake path starts the
   **device-default** ringtone right after the card displays:
   `const {startIncomingRingtone} = require('./incomingRingtone') …; startIncomingRingtone(p.callId);`
3. Both fire in the same JS context on a warm-background ring. The server _always_ sends the VoIP
   wake, even when the callee socket looks online —
   `apps/messenger-service/src/gateway/messenger.gateway.ts:1231-1236`: _"N-01 — ALWAYS queue the
   offer + fire the VoIP wake, not only when the socket-room probe says peer_offline"_, and the
   comment's own de-dupe claim only covers the card: _"the client dedupes by callId (notifee id
   `bravo-call-<callId>`; the foreground onMessage ignores voip-wake)"_.
4. The FCM background handler runs both surfaces unconditionally —
   `src/modules/messenger/push/fcmBootstrap.ts:1516-1533` (`showIncomingCallNotif({…})`) — while
   the live WS `call.offer` independently navigates to CallScreen
   (`src/navigation/MainNavigator.tsx:639-654`, `setIncomingCallHandler`), so CallScreen mounts and
   its ring effect runs _while backgrounded_.
5. `src/modules/messenger/push/incomingRingtone.ts:37-58` exposes only `start`/`stop`, with **no
   state** anyone can query — there is currently no way for the in-app surface to know the native
   ring owns the call.
6. Foreground-only and killed-only paths are already single-source, which is why this is
   warm-background-specific: `fcmBootstrap.ts:284` — `if (kind === 'voip-wake') { return; } // live
WS call.offer drives the ring UI` (foreground = in-app tone only); killed app = notifee/native
   ring only (no CallScreen).

Extra (audit under-scope): `src/screens/messenger/IncomingGroupCallScreen.tsx:81-111` has the same
unguarded `void tones.startRingtone();`, and group wakes ring natively under the same id
(`fcmBootstrap.ts:1486-1499`, _"Group rings reuse the roomId as the callId (gateway contract)"_).

## Mechanism

1. Caller sends `call.offer`. Gateway forwards it over WS **and** fires `sendVoipWake`
   unconditionally (`messenger.gateway.ts:1290`).
2. Callee's app is alive but backgrounded (screen off / user in another app).
3. FCM data message lands in `messaging().setBackgroundMessageHandler`
   (`fcmBootstrap.ts:1400`) — the background handler, not `onMessage`, because the app is not
   foreground. It verifies the HMAC, caches the payload, and calls `showIncomingCallNotif`
   (`:1525`) → `notifee.displayNotification` → `startIncomingRingtone(p.callId)`
   (`callNotification.ts:450`) → `BravoRingtoneModule.start` loops the **device-default ringtone**
   (`android/app/src/main/java/com/bravosecure/app/BravoRingtoneModule.kt:83-95`).
4. In the same process the WS is still up, so `callDispatcher` delivers the same `call.offer` to
   the handler installed by `MainNavigator` (`MainNavigator.tsx:499`), which navigates to
   `CallScreen` with `isIncoming: true`.
5. CallScreen mounts (React keeps rendering while backgrounded), `isRinging` is true, and the
   effect at `CallScreen.tsx:865` starts the **bundled `assets/ringtone.wav`** through expo-av at
   volume 1.0 on the loudspeaker (`bravoTones.ts` `startRingtone`) **and** kicks a repeating
   `Vibration.vibrate` pattern on top of the notification channel's own `vibrationPattern`
   (`callNotification.ts:441`, `RING_NOTIF_VIBRATION`).
6. Result: two unsynchronised looping ringtones (one on the RINGTONE stream, one on the MEDIA
   stream via expo-av) plus double vibration, until the user acts or the 45s timeout fires.

Group variant: identical, with `sfu.ring` → `IncomingGroupCallScreen` (ring effect at
`IncomingGroupCallScreen.tsx:81`) against a native ring keyed on the same `roomId`.

Why the audit's option (a) alone is wrong: an `AppState === 'active'` gate makes the in-app tone
silent while backgrounded, but there is a warm path where **no** native ring exists — a
foreground WS ring that the user then backgrounds (the foreground `onMessage` deliberately drops
`voip-wake` at `fcmBootstrap.ts:284`, so nothing native is playing). With a bare AppState gate that
user gets total silence the moment they press Home. Ownership must key on _"is the native ring
actually playing for this callId"_, not on AppState.

## Fix

Single-owner model: **the native device ringtone wins while it owns the callId; the in-app tone
takes over the instant the native one stops** (which the existing single dismiss funnel
`dismissCallNotif` already guarantees on tap / accept / decline / hangup). Client-only. No wire
format, no schema, no server change.

### 1. `src/modules/messenger/push/incomingRingtone.ts` — make ownership observable

**Anchor A** (verbatim, current file):

```ts
export function startIncomingRingtone(callId: string): void {
  try {
    const mod = native();
    if (!mod) {
      return;
    }
    mod.start(callId, RING_TIMEOUT_MS);
    console.log('[bravo.ring] start call=' + callId);
  } catch (e) {
    console.warn('[bravo.ring] start failed:', (e as Error).message);
  }
}

/** callId null = stop whatever is ringing (defensive sweep on logout/teardown). */
export function stopIncomingRingtone(callId: string | null, reason: string): void {
  try {
    const mod = native();
    if (!mod) {
      return;
    }
    mod.stop(callId);
    console.log('[bravo.ring] stop reason=' + reason + ' call=' + (callId ?? 'any'));
  } catch (e) {
    console.warn('[bravo.ring] stop failed:', (e as Error).message);
  }
}
```

**Replacement**:

```ts
type RingListener = () => void;

let activeRing: {callId: string; at: number} | null = null;
const ringListeners = new Set<RingListener>();

function notifyRingListeners(): void {
  for (const l of [...ringListeners]) {
    try {
      l();
    } catch {
      /* a bad listener must never break the ring path */
    }
  }
}

/**
 * NA-06 — true while BravoRingtoneModule is looping the device-default
 * ringtone for `callId`. Self-expires at RING_TIMEOUT_MS because the native
 * guardian auto-stops there without calling back into JS.
 */
export function isNativeRingActive(callId: string): boolean {
  if (!activeRing || activeRing.callId !== callId) {
    return false;
  }
  if (Date.now() - activeRing.at >= RING_TIMEOUT_MS) {
    activeRing = null;
    return false;
  }
  return true;
}

/**
 * NA-06 — drive an in-app ringtone that YIELDS to the native device-default
 * ring. `onOwn(true)` = the in-app surface should make noise; `onOwn(false)` =
 * the native ring owns this call. Fires immediately with the current verdict
 * and again on every ownership flip. Returns an unsubscribe.
 */
export function bindInAppRingOwnership(
  callId: string | undefined,
  onOwn: (owns: boolean) => void,
): () => void {
  let owns: boolean | null = null;
  const apply = () => {
    const next = !(callId && isNativeRingActive(callId));
    if (next === owns) {
      return;
    }
    owns = next;
    onOwn(next);
  };
  apply();
  ringListeners.add(apply);
  return () => {
    ringListeners.delete(apply);
  };
}

export function startIncomingRingtone(callId: string): void {
  try {
    const mod = native();
    if (!mod) {
      return;
    }
    mod.start(callId, RING_TIMEOUT_MS);
    activeRing = {callId, at: Date.now()};
    console.log('[bravo.ring] start call=' + callId);
    notifyRingListeners();
  } catch (e) {
    console.warn('[bravo.ring] start failed:', (e as Error).message);
  }
}

/** callId null = stop whatever is ringing (defensive sweep on logout/teardown). */
export function stopIncomingRingtone(callId: string | null, reason: string): void {
  const wasActive = activeRing !== null && (callId === null || activeRing.callId === callId);
  if (wasActive) {
    activeRing = null;
  }
  try {
    const mod = native();
    if (!mod) {
      return;
    }
    mod.stop(callId);
    console.log('[bravo.ring] stop reason=' + reason + ' call=' + (callId ?? 'any'));
  } catch (e) {
    console.warn('[bravo.ring] stop failed:', (e as Error).message);
  } finally {
    if (wasActive) {
      notifyRingListeners();
    }
  }
}
```

Notes: `if (!mod) {return;}` sits inside `try`, so the `finally` still notifies. When the native
module is absent (iOS / old APK / unit tests) `activeRing` is never set, so `isNativeRingActive` is
always false and the in-app tone behaves exactly as today — that is the intended degrade.

### 2. `src/screens/messenger/CallScreen.tsx` — yield the in-app ring

**Anchor B** (verbatim, `CallScreen.tsx:865-875`):


**Replacement**:

```tsx
useEffect(() => {
  if (!isRinging) {
    return;
  }

  const tones =
    require('@/modules/messenger/runtime/bravoTones') as typeof import('@/modules/messenger/runtime/bravoTones');
  const ring =
    require('@/modules/messenger/push/incomingRingtone') as typeof import('@/modules/messenger/push/incomingRingtone');
  // Why: on a warm-background ring the notifee wake path is ALREADY looping
  // the device-default ringtone for this callId (NA-06). Stay silent while it
  // owns the call; take over the instant the dismiss funnel stops it.
  const unbind = ring.bindInAppRingOwnership(callId, owns => {
    if (owns) {
      void tones.startRingtone();
      Vibration.vibrate([0, 800, 1200, 800], true);
    } else {
      void tones.stopRingtone();
      Vibration.cancel();
    }
  });
  return () => {
    unbind();
    void tones.stopRingtone();
    Vibration.cancel();
  };
}, [isRinging, callId]);
```

`callId` is already destructured from `route.params` at `CallScreen.tsx:107` and is stable for the
life of a mount, so adding it to the dep array cannot re-fire the effect mid-ring. `bravoTones`'
`startSlot`/`stopSlot` are explicit state machines (`idle|starting|started|stopping`), so a
redundant start/stop from an ownership flip is a no-op — no unload race introduced.

```tsx
const tones =
  require('@/modules/messenger/runtime/bravoTones') as typeof import('@/modules/messenger/runtime/bravoTones');
const ring =
  require('@/modules/messenger/push/incomingRingtone') as typeof import('@/modules/messenger/push/incomingRingtone');
// Why: the group voip-wake rings natively under the roomId (the gateway
// reuses it as the callId), so an in-app tone here would double it (NA-06).
let vibTimer: ReturnType<typeof setTimeout> | null = null;
const unbindRing = ring.bindInAppRingOwnership(roomId, owns => {
  if (owns) {
    void tones.startRingtone();
    vibTimer = setTimeout(() => {
      Vibration.vibrate([0, 800, 1200, 800], true);
    }, 50);
  } else {
    if (vibTimer) {
      clearTimeout(vibTimer);
      vibTimer = null;
    }
    void tones.stopRingtone();
    Vibration.cancel();
  }
});
```

### Schema / wire / back-compat

None. No SQLCipher schema touched (no store file changes → no version bump), no outbox row shape,
no relay DTO, no notification `data` field added or removed, no server change. Old and new clients
interoperate unchanged; the native `BravoRingtoneModule` API (`start`/`stop`) is untouched so no
APK/native rebuild is required beyond the normal JS bundle.

Callers of the changed module (all verified, none need edits):

- `src/modules/messenger/push/callNotification.ts:449-450` (`startIncomingRingtone` in
  `showIncomingCallNotif`) and `:577-578` (`stopIncomingRingtone` in `dismissCallNotif`) — the only
  production callers. Both keep their existing signature; the new state is a pure side effect.
- `dismissCallNotif` fan-in (every path that must clear ownership): `fcmBootstrap.ts:419, 440, 588,

- Tests that mock `callNotification`: `callAcceptLatch.test.ts`, `callHangupWhileRinging.test.ts`,
  `iceFailedReconnect.test.ts` — they mock the module wholesale, unaffected.

What could regress:

- **Silent/vibrate ringer mode.** `BravoRingtoneModule.kt:58-61` skips playback when
  `ringerMode != RINGER_MODE_NORMAL`, but JS still marks the ring "owned", so a warm-background
  ring on a silenced phone now produces **no** in-app WAV either. That is the OS-correct behaviour
  and already what the killed-app path does today, but it _is_ a behaviour change (today the expo-av
  WAV plays through the media stream and ignores the ringer switch). Call it out at review; if
  product wants the old behaviour, the correct fix is a native `isRinging(callId): Promise<boolean>`
  on `BravoRingtoneModule`, not weakening the JS flag.
- **Cold launch via `fullScreenAction` on a locked device** (killed app). If the notifee handler
  ran in a JS context whose module registry is not shared with the launched activity's context,
  `activeRing` is empty in the UI context and the in-app tone plays over the native one — i.e.
  exactly today's behaviour, no worse. Worth a device check (§Tests, device row 3).
- `IncomingGroupCallScreen`'s ring effect is a `[]` one-shot with an eslint-disable; the edit adds
  no new deps, so the disable comment stays valid and the 45 s missed-group-call timeout is
  untouched.

Overlapping findings in the same audit:

  lines above Anchor B. Adjacent, not overlapping; if NA-02 lands first re-locate Anchor B by
  content. If §Fix item 4 is taken, it edits the _same_ effect NA-02 edits — sequence them.

## Risk

- **Module-level mutable state across JS contexts.** The whole design assumes the FCM background
  handler and the UI share one module registry. That is true for warm-background (the documented
  and targeted case) and I verified nothing else depends on it — but a reviewer should push on the
  killed-app/headless context (`fcmHeadless.ts`), where the flag may be invisible. The failure mode
  is "behaves like today", not "worse than today"; confirm that framing before merging.
- **Behaviour change on a silenced phone** (see Blast radius). This is the one user-visible
  difference beyond killing the double ring, and it is deliberate. Do not "fix" it by ignoring the
  ownership flag.
- **The audit's own suggested fix is the wrong one.** Reject any diff that gates the in-app tone on
  `AppState === 'active'`: the foreground-ring-then-Home path has no native ring (dropped at
  `fcmBootstrap.ts:284`) and would go silent. Also reject the mirror-image suggestion "skip the
  native one when the in-app surface owns the callId" — in warm background the in-app surface is
  invisible, and the native ring is the one that respects ringer mode, the RINGTONE audio stream,
  and survives the JS context dying.
- **`finally` + early `return` in `stopIncomingRingtone`** is intentional (notify must run even when
  the native module is absent). Reviewers often flag this as a mistake.
- **Listener leak.** `bindInAppRingOwnership` returns an unsubscribe that both screens call from
  effect cleanup; verify neither edit drops the `unbind()`/`unbindRing()` call, or a remounting
  ring screen accumulates listeners that call `startRingtone` on a dead mount.
- No security surface: no crypto, no envelope/AAD, no cert, no vault gate, no logging of message
  bodies or key material (the only new log lines are the pre-existing `[bravo.ring]` callId lines,
  which `logAudit.test.ts` already tolerates).
