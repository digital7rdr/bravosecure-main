# OM-07 - SN-04 unreachable reschedule is frozen at 1s (no streak counter) and the drain sweep has no wall-clock bound

## Verdict

**CONFIRMED** (mechanism exactly as described; line numbers drifted by ~1).

- `src/modules/messenger/store/sqlOutboxStore.ts:235-245` — the unreachable branch indexes the
  backoff table with `row.attempts` and writes **only** `next_retry_at`:
  ```ts
  if (opts?.unreachable) {
    const delay = BACKOFF_MS[Math.min(row.attempts, BACKOFF_MS.length - 1)];
    await this.db.execute(
      `UPDATE outbox SET next_retry_at = ?
  ```
  `attempts` is never incremented on this path (that is the whole point of SN-04), so for the
  overwhelmingly common row (`attempts = 0`, never server-rejected) the delay is
  `BACKOFF_MS[0]` = **1 000 ms on every single unreachable failure, forever**.
- The code's own comment at `sqlOutboxStore.ts:233-234` asserts the opposite of what it does:
  _"Backoff still applies, so an offline device costs at most one attempt per 5 minutes per row
  rather than a hot loop."_ — false; the schedule never advances past slot 0.
- Sweep cadence: `src/modules/messenger/runtime/productionRuntime.ts:1612-1614`
  `const outboxRetryTimer = setInterval(() => { void drainOutbox(...); }, 60_000);` — every parked
  row (1 s < 60 s) is due on **every** tick.
- Serial cost per row: `drainOutbox` awaits `relay.send` inside a `for (const row of rows)` loop
  (`productionRuntime.ts:7406`, `7476`) behind a single `drainOutboxInflight` guard
  (`:7400-7401`); `RelayHttpClient` (`@bravo/messenger-core`) issues it through
  `fetchWithTimeout` with `TRANSPORT_TIMEOUT_MS = 20_000`
  (`packages/messenger-core/src/transport/fetchWithTimeout.ts:18`). A black-holed route
  (dead-zone / captive Wi-Fi) therefore burns the **full 20 s per row, serially, every 60 s**.
- No bound on the sweep exists: the loop's only early exit is `if (!isOurEpoch()) {return;}`
  (`:7407`). N queued rows = N × 20 s of radio-on wall time per sweep.

Audit's fix direction is right, but **incomplete in a way that would ship a regression** — see
"Fix, part 3": once the offline backoff actually grows to 5 min, `dueRows` (which filters
`next_retry_at <= now`) will _skip parked rows on reconnect_, so a user leaving a dead zone would
wait up to 5 minutes for their queued messages instead of the near-instant send they get today.
The unpark-on-connect step is mandatory, not optional.

## Mechanism

1. User is in a dead zone — associated Wi-Fi / 1 bar of GPRS, TCP connects but the upstream is
   black-holed. This is the _worst_ case, not "airplane mode": `fetch` neither resolves nor
   rejects, so the SN-01 `AbortController` fires at 20 s.
2. `drainOutbox` (boot, every `socket.on('connect')`, and the 60 s interval) pulls `dueRows()`.
3. Row 1: `relay.send` → 20 s → `AbortError`. `isUnreachableError` returns `true`
   (`sqlOutboxStore.ts:72`).
4. `recordAttempt(..., {unreachable: true})` reads `attempts` (0), computes
   `BACKOFF_MS[0] = 1_000`, writes `next_retry_at = now + 1s`, leaves `attempts = 0`.
5. Loop continues to row 2, 3, … N — each burns another 20 s. Nothing aborts the sweep, so a
   10-row queue holds the radio and the inflight guard for **200 s**; the 60 s timer ticks fire
   into the `drainOutboxInflight` early-return and are lost, so the sweep is effectively
   _continuous_ for as long as the device stays in the dead zone.
6. Every row's `next_retry_at` is 1 s old by the time the sweep ends, so the next tick re-runs the
   identical 200 s burn. The intended de-escalation to a 5-minute cadence never happens.
7. Cost: continuous radio wake + CPU + a permanently-held `drainOutboxInflight`, which also blocks
   the _legitimate_ reconnect drain from starting promptly when the network returns.

Note the fast-fail variant (true airplane mode) is comparatively benign — `fetch` rejects in
milliseconds, so the sweep is cheap even though it re-runs every 60 s. The defect bites hardest on
the slow/black-holed path, which is exactly the network state a dead-zone user is in.

## Fix

Three parts. Parts 1 and 3 are one unit (do not ship 1 without 3). Part 2 is independent and could
ship alone.

adds a second counter so the offline schedule can escalate without touching the server-rejection
budget that SN-04 deliberately protects.

### Part 2 — bound the sweep's wall time and abort a dead-zone sweep

**New file: `src/modules/messenger/runtime/outboxDrainBudget.ts`**

(Mirrors the `outboxCertFreshness.ts` precedent: pure decision in a tiny import-free module so it
is unit-testable without standing up the 8k-line runtime.)

```ts
/**
 * OM-07 — how long one outbox sweep may run, and when to abandon it.
 *
 * Kept in its own tiny module (no native/runtime imports) so the decision can be
 * unit-tested without standing up the messenger runtime — same rationale as
 * `outboxCertFreshness.ts`.
 *
 * Background: `drainOutbox` ships rows SERIALLY behind a single inflight guard,
 * and a black-holed route makes each `relay.send` hang for the full SN-01 20s
 * transport deadline. With N queued rows that is N x 20s of radio-on time per
 * 60s sweep, and the sweep restarts the moment it ends.
 */

/**
 * Wall-clock budget for one sweep. Half the 60s sweep interval, so a truncated
 * sweep still ends before the next tick. Checked BETWEEN rows, so one in-flight
 * row may overrun it by up to the transport deadline — a soft bound by design;
 * aborting a row mid-flight would risk a duplicate the relay's (recipient,
 * clientMsgId) dedup already covers but the UI does not.
 */
export const OUTBOX_DRAIN_BUDGET_MS = 30_000;

/**
 * Consecutive unreachable failures after which the sweep gives up: the network
 * is down, not the peer, so every remaining row would pay the same 20s. Two
 * rather than one so a single flaky row cannot abort a sweep that would
 * otherwise deliver.
 */
export const OUTBOX_DRAIN_UNREACHABLE_STREAK = 2;

export type DrainStop = 'continue' | 'budget' | 'unreachable';

export function shouldStopDrain(
  state: {startedAtMs: number; unreachableStreak: number},
  nowMs: number = Date.now(),
): DrainStop {
  if (state.unreachableStreak >= OUTBOX_DRAIN_UNREACHABLE_STREAK) {
    return 'unreachable';
  }
  if (nowMs - state.startedAtMs >= OUTBOX_DRAIN_BUDGET_MS) {
    return 'budget';
  }
  return 'continue';
}
```

### Part 3 — unpark on proven reachability (mandatory companion to Part 1)

Without this, Part 1 regresses the leave-the-dead-zone case: `dueRows` filters
`next_retry_at <= now` (`sqlOutboxStore.ts:119`), so rows parked 5 minutes out are skipped by the
reconnect drain and the user's queued messages sit for minutes after signal returns. Today they go
immediately _because_ the backoff is frozen at 1 s — that accidental behaviour must be replaced by
an explicit one.

**File: `src/modules/messenger/store/sqlOutboxStore.ts`** — add after `resetFailed`:

```ts
  /**
   * OM-07 — a fresh socket connect proves the network is back, so drop the
   * offline parking for every pending row. `dueRows` only returns rows past
   * `next_retry_at`, so without this the escalated unreachable backoff (up to
   * 5 min) would delay the reconnect drain that used to fire instantly.
   * Deliberately does NOT touch `attempts` or `status='failed'` rows — those
   * are the server-rejection budget and only the user's tap-to-retry clears
   * them (`resetFailed`).
   */
  async clearUnreachableBackoff(now: number = Date.now()): Promise<void> {
    await this.db.execute(
      `UPDATE outbox
          SET unreachable_attempts = 0, next_retry_at = ?
        WHERE status = 'pending' AND unreachable_attempts > 0`,
      [now],
    );
  }
```

### Wire format / back-compat

No wire change. Nothing crosses the client↔server boundary; `unreachable_attempts` is a local
SQLCipher column and the relay never sees it. Old-server / new-client and new-server / old-client
are both unaffected. Local-only schema bump 14 → 15 is forward-only (`db.ts:441`,
`runMigrations` runs `ADD COLUMN` idempotently) and there is no downgrade path in the app, matching
every prior bump.

## Risk

- **The regression this fix can cause is the one the fix creates, not the one it removes.** A
  reviewer should check Part 3 exists and is wired to `state === 'connected'`. Landing Parts 1+2
  alone converts a battery bug into a "my messages sent 4 minutes late" bug, which users will
  notice far more.
- **Socket flap amplification.** `clearUnreachableBackoff` on every `connected` transition means a
  connect/disconnect loop re-arms every parked row each cycle. Bounded by socket.io's own reconnect
  backoff (and a socket that keeps completing handshakes is by definition reachable), but it is the
  sharpest edge in the diff. If it proves noisy, gate it behind a per-connect timestamp
  (e.g. skip if the last unpark was <30 s ago) rather than removing it.
- **Migration ordering.** The `ALTER` must be in the `fromVersion < 15` block and **not** in the
  `DDL` array — a DDL-level ALTER runs before `runMigrations`, and the `fromVersion < 7` rebuild's
  hard-coded column list would silently drop the column again on a v6→v15 upgrade. Verify the new
  block sits after the `fromVersion < 14` block.
- **`unreachable_attempts` grows without bound by design.** That is intentional (SN-04's contract
  is that an offline stretch must never kill a row; the relay holds envelopes ~30 days), but a
  reviewer should confirm nothing else reads the counter as a failure signal — only `backoffFor`
  consumes it, and it saturates at index 4.
- **The budget is soft.** `shouldStopDrain` is evaluated _between_ rows, so a sweep can exceed 30 s
  by one transport timeout. Aborting mid-flight was rejected deliberately: the relay dedups on
  `(recipient, clientMsgId)` so a duplicate ship is safe on the wire, but the local row would have
  no acceptance signal and the UI tick would lag. Do not "improve" this into an in-flight abort.
- **Do not fold this into `attempts`.** The obvious-looking simplification — increment `attempts`
  on unreachable and just raise `MAX_ATTEMPTS` — re-opens SN-04 exactly: a long dead zone would
  eventually flip rows to `status='failed'`, and `dueRows` never selects those, so reconnecting
  would send nothing until the user tapped retry on each bubble.
