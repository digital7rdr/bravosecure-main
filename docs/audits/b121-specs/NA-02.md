# NA-02 - Dead-offer answer path has no terminal state: "Answering…" forever

## Verdict

**CONFIRMED** (mechanism exact; line numbers drifted a few lines).

1. `src/modules/messenger/webrtc/useCall.ts:432-434` — the pre-controller bail is
   still there, verbatim:
   ```ts
   if (direction === 'incoming' && !incomingSdp) {
     return;
   }
   ```
   No controller, no `setActiveCall(...)` (that lives at `useCall.ts:840`, _after_ the
   bail), so the call registry stays empty for this callId.
2. `src/modules/messenger/webrtc/useCall.ts:154` — `const [state, setState] =
useState<CallState>(direction === 'incoming' ? 'ringing' : 'idle');`. The bail leaves
   `state === 'ringing'` permanently: nothing can move it (the only `setState('failed')`
   is the boot `catch` at `useCall.ts:902`, which the early `return` skips, and the
   registry mirror `onActiveCallChange` at `useCall.ts:402` is installed **only** in the
   adopt branch).
3. `src/screens/messenger/CallScreen.tsx:802-805` — the 45s accept-expiry is still a
   pure `console.warn` + `return`:
   ```ts
   if (Date.now() - acceptIntentAtRef.current > 45_000) {
     console.warn(
       '[bravo.call] accept intent expired (>45s before controller was ready) — not answering a dead offer',
     );
     return;
   }
   ```
   It is inside `useEffect(..., [autoAccept, userAccepted, isIncoming, incomingSdpKey,
liveCall.state])` (`CallScreen.tsx:831`) — with no controller none of those deps ever
   change again, so the branch is not even _re-evaluated_, let alone acted on. There is
   no timer.
4. `src/screens/messenger/CallScreen.tsx:781` — `const isRinging = isIncoming &&
liveCall.state === 'ringing' && !autoAccept && !userAccepted;` → with `autoAccept`
   true, `isRinging` is false, so `callState` (`CallScreen.tsx:765-768`) collapses to
   `'connecting'` and the label at `CallScreen.tsx:2062` / `:2504` renders
   `isIncoming ? 'Answering…' : 'Calling…'` — forever. Neither terminal effect
   (`CallScreen.tsx:1428` `'failed'`, `:1457` `'ended'`) can fire.
5. Both external "the call is dead" lanes are also blind to this screen:
   `callDispatcher.ts` `case 'call.hangup'` → `endZombieSession(cid, 'call.hangup')`
   → `reg.getActiveCall()` returns **null** (never registered), so it no-ops; and
   `fcmBootstrap.ts:782` `handleCallCancel()` only dismisses notifee / Telecom /
   the cache — it never touches a mounted `CallScreen`.

Net: user taps **Answer**, the offer SDP never lands, and the screen is a dead end with
only hardware-back (which, via `beforeRemove` at `CallScreen.tsx:745`, **minimizes**
rather than ends — `liveStates` includes `'ringing'`, so it hands them a floating overlay
for a call that does not exist).

## Mechanism

1. Caller dials. Server VoIP-wakes the callee (FCM data wake carries **no SDP** —
   `fcmBootstrap.ts:1191-1199` explicitly hydrates it from `incomingCallCache` because
   "the FCM voip-wake data never carries the offer SDP").
2. Callee taps **Answer** on the notification → `fcmBootstrap` navigates to `CallScreen`
   with `autoAccept: true` and `incomingSdp: hydratedSdp`. On a cold/killed launch (or a
   WS that has not reconnected) the cache is empty → `incomingSdp === undefined`.
3. `CallScreen` mounts. `useCall` boot runs, hits
   `if (direction === 'incoming' && !incomingSdp) { return; }` → **no controller, no
   signalling registration, no registry entry**. `liveCall.state` is stuck at `'ringing'`.
4. `isRinging` is false (autoAccept) → the ring UI with Answer/Decline is suppressed →
   the only visible affordance is the End button; status reads **"Answering…"**.
5. The offer never arrives (WS never reconnects, or the server already expired the
   45s ring window and purged the queued offer — `messenger.gateway.ts` N-02
   `clearPendingCallArtifacts`). `incomingSdpKey` never flips, `liveCall.state` never
   changes → the auto-accept effect never re-runs.
6. Even when the caller gives up:
   - WS `call.hangup` → `callDispatcher` finds no `sig` **and** `endZombieSession` finds
     no registry entry → the screen is untouched.
   - FCM `call-cancel` → `handleCallCancel` dismisses the notification and tombstones the
     cache → the screen is untouched.
7. Result: "Answering…" indefinitely; back-press minimizes into a phantom floating
   overlay; the chat thread gets no missed-call record because the unmount call-record
   effect (`CallScreen.tsx:1382-1424`, which _would_ classify this correctly as
   `'missed'`) never runs.

## Fix

Three files, ~70 lines total. No wire change, no schema change, no crypto touched.

The design deliberately reuses what already exists:

- the unmount call-record effect already files incoming/never-connected as `'missed'`,
  so we must **not** add a second bubble — we only need the screen to actually unmount;
- `declineIncomingCallBestEffort` is already the sanctioned null-controller teardown
  (B-102 A2) — hangup from the cached payload + clear notifee + Telecom + cache + latch;
- every "this call is dead" lane (WS `call.hangup`, FCM `call-cancel`, Telecom end,
  decline, natural end) already funnels through `clearIncomingCallPayload`, which
  tombstones the callId. That tombstone is therefore a ready-made, cross-lane dead
  signal a controller-less screen can read.

### F1. `src/modules/messenger/push/incomingCallCache.ts` — expose the tombstone

**Anchor** (verbatim, end of file before the test helper):

```ts
export function clearIncomingCallPayload(callId: string): void {
  if (cache.delete(callId)) {
    tombstones.set(callId, Date.now());
  } else {
    // Even if the entry was already gone, tombstone it so a late
    // re-set is rejected — covers the "peer hung up before we saw
    // the offer" race.
    tombstones.set(callId, Date.now());
  }
}
```

**Insert immediately after it:**

```ts
/**
 * NA-02 — "this callId is terminal". Every cancel lane (WS `call.hangup`,
 * FCM `call-cancel`, Telecom end, decline, natural call end) routes through
 * `clearIncomingCallPayload`, which tombstones. A ring screen whose offer SDP
 * never arrived has no controller and no `callRegistry` entry, so this
 * tombstone is the only cross-lane "the call is dead" signal it can read.
 * Never set on accept — an in-app-answered call keeps its cached payload for
 * the whole call.
 */
export function isIncomingCallDead(callId: string): boolean {
  gc(Date.now());
  return tombstones.has(callId);
}
```

Back-compat: additive export only.

// rest of the machinery while `useCall` is stuck pre-controller (no
// controller ⇒ hangup() is a no-op; no callRegistry entry ⇒ the dispatcher's
// endZombieSession and the FCM call-cancel path both no-op):
//   1. the accept intent aged past ACCEPT_INTENT_TTL_MS — the offer is dead;
//   2. the callId got tombstoned — the caller cancelled over WS or FCM.
// Disarms the instant accept() is fired (autoAcceptedRef) or the user
// ends/declines (hangupInFlightRef), so a live call can never be killed here.
useEffect(() => {
  if (!isIncoming || !callId || deadOffer) {
    return;
  }
  if (autoAcceptedRef.current || hangupInFlightRef.current) {
    return;
  }
  if ((autoAccept || userAccepted) && acceptIntentAtRef.current === null) {
    acceptIntentAtRef.current = Date.now();
  }
  let timer: ReturnType<typeof setInterval> | null = null;
  const stop = () => {
    if (timer) {
      clearInterval(timer);
      timer = null;
    }
  };
  const tick = () => {
    if (autoAcceptedRef.current || hangupInFlightRef.current || dismissedRef.current) {
      stop();
      return;
    }
    let peerCancelled = false;
    try {
      const cache =
        require('@/modules/messenger/push/incomingCallCache') as typeof import('@/modules/messenger/push/incomingCallCache');
      peerCancelled = cache.isIncomingCallDead(callId);
    } catch {
      /* cache unavailable (tests) — the deadline still fires */
    }
    const startedAt = acceptIntentAtRef.current;
    const expired = startedAt !== null && Date.now() - startedAt > ACCEPT_INTENT_TTL_MS;
    if (!peerCancelled && !expired) {
      return;
    }
    console.warn(
      `[bravo.call] dead-offer watchdog fired cid=${callId.slice(0, 8)} ` +
        `reason=${peerCancelled ? 'peer-cancelled' : 'accept-intent-expired'}`,

// surface (reusing the B-102 null-controller path), let the user read the
// "Couldn't connect" label for a beat, then pop. The unmount call-record
// effect files the leg as an incoming 'missed' call — no extra bubble here.

    return;

  Vibration.cancel();

        require('@/modules/messenger/push/fcmBootstrap') as typeof import('@/modules/messenger/push/fcmBootstrap');
      fb.declineIncomingCallBestEffort(callId, 'failed');

      /* push layer unavailable — the pop below still runs */

      return;

    dismissedRef.current = true;

      /* ignore */

  }, 1_800);

## Blast radius

**Files edited**

- `src/screens/messenger/CallScreen.tsx` — new state `deadOffer`, two new effects, one
  const, two label branches, one constant swap.
- `src/modules/messenger/push/incomingCallCache.ts` — one additive export.
- `src/modules/messenger/push/fcmBootstrap.ts` — `declineIncomingCallBestEffort` gains an
  optional `reason` param (default preserves current behaviour).

**Callers of the changed function** — `declineIncomingCallBestEffort` has exactly two
production call sites, both in `CallScreen.tsx` (`declineCall`, and the new terminal
effect) plus `src/modules/messenger/__tests__/callAcceptLatch.test.ts`. All existing
callers keep the `'declined'` default.

**What could regress**

1. **Killing a live call.** The watchdog must disarm on `autoAcceptedRef.current`. If
   `accept()` is fired but the state machine is slow, the interval keeps ticking — the
   guard is checked _inside_ `tick`, so it stops on the next tick. Verify the tombstone
   is never set on the accept path: `fcmBootstrap.ts:410-419` explicitly documents "an
   in-app-answered call keeps its cached payload for the whole call", and no accept path
   calls `clearIncomingCallPayload`. This is the single highest-risk assumption in the fix.
2. **Double-pop.** `deadOffer`'s pop and `declineCall`'s 800ms pop both guard on
   `dismissedRef` — the existing de-dupe. A `deadOffer` firing during a user decline is
   cosmetic only (`hangupInFlightRef` check in `tick` prevents it).
3. **Duplicate missed-call bubble.** The unmount record uses the stable id
   `call-${callId}`; `callDispatcher.appendMissedCallBubble` uses `missed-${callId}`.
   Different ids ⇒ **two** bubbles are possible if the caller's WS hangup lands while
   this screen is mounted. That is a _pre-existing_ overlap (any decline-while-mounted
   hits it) and is out of scope for NA-02, but a reviewer will spot it — flag it as a
   follow-up rather than widening this diff.
4. **`ACCEPT_INTENT_TTL_MS` hoisting** — the file has module-level consts already;
   putting it inside the component would re-create it each render (harmless) but the
   watchdog dep array must not include it.

**Overlapping findings** — SRV-03 (connect-time drain of pending call offers) reduces how
often this path is reached but does not remove it; NA-02 is the safety net and the two
are independent edits (server vs. client). NA-06 and any other `CallScreen.tsx` edit in
this batch will conflict textually — sequence them.

## Risk

Things a reviewer should be suspicious of:

1. **The tombstone-as-dead-signal assumption.** The whole cross-lane half of the fix
   rests on "no accept path ever calls `clearIncomingCallPayload`". I audited all 11 call
   sites (`fcmBootstrap` ×6, `callRegistry:230`, `callDispatcher:320`, `useCall:618`,
   plus the cache itself) and every one is a terminal event — but this is exactly the
   kind of invariant a future edit breaks silently. The negative Jest case above is the
   guard; a reviewer should insist on it.
2. **Interval-based watchdog vs. Doze.** RN freezes JS timers when the app is
   backgrounded (see the B-100/B-101 notes). If the user backgrounds the stuck screen,
   the 1s interval stalls and the deadline fires late on resume — that is acceptable
   (the exit still happens, just on resume) but it means the fix does **not** guarantee a
   45s wall-clock exit. Using `Date.now()` deltas (not tick counting) is what makes the
   late fire still correct; do not "optimize" that into a countdown.
3. **`reason: 'failed'` reaching the caller.** The gateway forwards `reason` verbatim; an
   older caller build maps any non-`declined` reason through
   `reportEnded(cid, reason === 'failed' ? 'failed' : 'remoteEnded')` in
   `callDispatcher.ts` — already handled. But confirm the caller's `CallScreen` failed-
   branch copy ("Connection lost — couldn't reconnect") is acceptable for this case; it is
   arguably better than "Declined", which is what ships today via the decline fallback.
4. **The 1.8s dwell before popping.** Long enough to read, short enough not to feel
   stuck. If product wants an Alert instead (matching the `'failed'` branch's
   `Alert.alert('Call ended', …)` at `CallScreen.tsx:1450`), that is a one-line swap —
   but it would need `@utils/alert`, **never** `Alert` from `react-native` (B-88 static
   sweep). The current draft deliberately avoids the dialog: the user is already looking
   at a full-screen call surface.
5. **Duplicate missed-call bubble** (blast-radius item 3) is real but pre-existing;
   resist fixing it inside this diff.
6. **Nothing here touches crypto, sealed sender, AAD, cert verification, the vault MFA
   gate, relay dwell, or any envelope shape** — no CLAUDE.md stop condition applies. The
   only wire value used is `reason: 'failed'`, an existing member of the
   `ServerCallHangup` union.
