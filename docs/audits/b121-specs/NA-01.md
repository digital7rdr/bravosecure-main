# NA-01 - FCM voip-wake clobbers the WS-seeded incomingCallCache entry (SDP / deviceId / conversationId erased)

## Verdict

**CONFIRMED** — reproduced in the current tree, at the exact lines the audit cited (no drift).

- `src/modules/messenger/push/incomingCallCache.ts:85` — `cache.set(p.callId, {...p, cachedAtMs: now});` is a full replace. There is no merge anywhere in the module; the only guard is the tombstone check above it.
- `src/navigation/MainNavigator.tsx:539-546` — the WS `call.offer` handler seeds the entry **with** SDP and routing:
  `cache.setIncomingCallPayload({callId: data.callId, callerName, kind: …, fromUserId: data.from.userId, remoteDeviceId: data.from.deviceId, incomingSdp: data.sdp, conversationId});`
- `src/modules/messenger/push/fcmBootstrap.ts:1493-1501` — the FCM bg-wake handler re-sets the SAME callId with **no** `incomingSdp`, **no** `remoteDeviceId`, and (for 1:1) `conversationId: undefined`:
  `const accepted = cache.setIncomingCallPayload({callId: …, callerName, kind: callKindStr, fromUserId, conversationId, roomId: isGroupKind ? … : undefined, roomToken});`
- The server guarantees both arrive: `apps/messenger-service/src/gateway/messenger.gateway.ts:1232-1291` — "N-01 — ALWAYS queue the offer + fire the VoIP wake, not only when the socket-room probe says peer_offline", and the 1:1 call passes `sendVoipWake(data.to.userId, data.callId, ctx.claims.sub, undefined, …)` — i.e. **no conversationId argument**, and `push.service.ts:1063-1077` sends **data-only** (no `notification` block) so `setBackgroundMessageHandler` _does_ run while the app is backgrounded-but-alive.
- The consumer that the audit calls out is real and is starved by exactly this: `fcmBootstrap.ts:1191-1197` — `let hydratedSdp = data.incomingSdp; if (!hydratedSdp) { … hydratedSdp = cache.getIncomingCallPayload(callId)?.incomingSdp; }` — the B-102 A1 fix hydrates the SDP **from the very entry the wake just wiped**.
- `fcmBootstrap.ts:284` — `if (kind === 'voip-wake') { return; } // live WS call.offer drives the ring UI` — the foreground path is immune, which is why this is a _backgrounded-only_ deterministic stall.

## Mechanism

App backgrounded, WS still healthy (the B-100/B-101 background-WS work keeps it alive):

1. Caller sends `call.offer`. Gateway forwards it over WS **and** unconditionally fires `sendVoipWake` (N-01), which is data-only + high priority.
2. WS frame lands first (it is forwarded synchronously before the push is queued). `MainNavigator`'s `setIncomingCallHandler` resolves the **canonical** conversation id (`resolveDirectConversationIdFromState`) and the real contact name, writes the full payload — **including `incomingSdp` and the caller's `remoteDeviceId`** — into `incomingCallCache`, and calls `reportIncomingCall` (Telecom).
3. 1–3 s later the FCM data message arrives. Because the app is backgrounded, `setBackgroundMessageHandler` runs **in the same JS VM**, so it touches the **same module-level `Map`**.
4. It verifies the HMAC, resolves a local name (or falls back to `'Bravo contact'`) and calls `setIncomingCallPayload` again for the same callId. `cache.set()` **replaces** the entry:
   - `incomingSdp` → `undefined` (the wake never carries SDP, by design),
   - `remoteDeviceId` → `undefined` (never on the wake at all),
   - `conversationId` → `undefined` for 1:1 (the gateway passes no conversationId on the `call.offer` path),
   - `callerName`/`kind` → possibly downgraded to the generic fallback / `'voice'`.
5. It then draws the notifee ring (`showIncomingCallNotif`), whose `data` block only contains what it was given — so the notification carries **no** `incomingSdp`, **no** `remoteDeviceId`, and **no** `conversationId` (`callNotification.ts:356-368` only copies fields that are truthy).
6. User taps **Answer**:
   - notifee path (`fcmBootstrap.ts:1191`): `data.incomingSdp` is absent → falls back to the cache → cache SDP is gone → navigates to `CallScreen` with `incomingSdp: undefined`, `remoteDeviceId: 1`, `conversationId: 'direct:<uid>'`. `autoAccept` fires with nothing to answer → the deterministic **"Answering…" stall**; if the offer is ever replayed, `call.answer` is addressed to the caller's device **1** (wrong device when the caller isn't on device 1) and the call log lands in a **synthetic duplicate thread** instead of the canonical one.
   - Telecom path (`navigateToIncomingCall`, `fcmBootstrap.ts:600-665`): reads the whole cached payload — same three fields missing, same outcome.
   - Decline path (`sendCallHangup`, `fcmBootstrap.ts:685-706`): `to.deviceId = payload.remoteDeviceId ?? 1` → decline can be routed to the wrong caller device, so the caller keeps ringing.

Order is not load-bearing for the fix: FCM-first/WS-second happens to work today only because the WS payload is a superset; the WS-first ordering (the common one on a healthy socket) is the broken one.

## Fix

Client-only. **No wire-format change, no server change, no persisted schema, no migration** — `incomingCallCache` is an in-memory `Map`. Old/new servers and old/new peers are unaffected.

### 1. `src/modules/messenger/push/incomingCallCache.ts` — make the setter merge-preserving

**Anchor (verbatim, current line 85):**

```ts
  cache.set(p.callId, {...p, cachedAtMs: now});
  return true;
}
```

**Replacement:**

```ts
  const prev = cache.get(p.callId);
  cache.set(p.callId, prev ? mergeIncoming(prev, p, now) : {...p, cachedAtMs: now});
  return true;
}
```

**Insertion — new helper, placed immediately above `setIncomingCallPayload` (after the `gc` function):**

```ts
// Why: NA-01 — the WS `call.offer` and the FCM voip-wake both seed the same
// callId while the app is backgrounded, and the wake carries no SDP / device
// id / conversationId. A plain replace erased what the offer had already
// delivered, so the answer tap hydrated an empty payload and stalled.
function mergeIncoming(
  prev: CachedIncomingCall,
  next: Omit<CachedIncomingCall, 'cachedAtMs'>,
  now: number,
): CachedIncomingCall {
  // The offer frame is the only writer that carries SDP; when the incoming
  // payload has none it is the (unsigned, display-only) push wake, so its
  // label/kind must not overwrite the authoritative ones.
  const pushOverOffer = !!prev.incomingSdp && !next.incomingSdp;
  return {
    callId: next.callId,
    callerName: pushOverOffer ? prev.callerName : next.callerName || prev.callerName,
    kind: pushOverOffer ? prev.kind : next.kind || prev.kind,
    fromUserId: next.fromUserId ?? prev.fromUserId,
    remoteDeviceId: next.remoteDeviceId ?? prev.remoteDeviceId,
    incomingSdp: next.incomingSdp ?? prev.incomingSdp,
    roomId: next.roomId ?? prev.roomId,
    roomToken: next.roomToken ?? prev.roomToken,
    conversationId: next.conversationId ?? prev.conversationId,
    cachedAtMs: now,
  };
}
```

Notes:

- `cachedAtMs: now` keeps today's TTL semantics (every `set` restarts the 60 s window). Do **not** switch to `prev.cachedAtMs` in this change — it would shorten the live-ring window for the second writer and is an unrelated behaviour change.
- The tombstone rejection above stays exactly as-is (it is the guard that stops a retried/stale callId from resurrecting anything). Merging happens strictly _after_ it.
- Field-wise merge lives in the setter, not at the call sites, so a future third writer cannot re-introduce the class.

**Insertion — new exported helper, placed immediately above `function installNotifeeHandlers()` (currently line 905):**

```ts
/**
 * NA-01 — the FCM voip-wake never carries SDP / caller device id, and (1:1)
 * never carries a conversationId, so a notification drawn from the wake has
 * none of them in its `data` block. The WS `call.offer` put all three in the
 * incoming-call cache; read them back before navigating. Exported for tests.
 */
export function resolveIncomingCallRoute(
  callId: string,
  data: {
    incomingSdp?: string;
    remoteDeviceId?: string;
    conversationId?: string;
    fromUserId?: string;
  },
): {conversationId: string; remoteDeviceId: number; incomingSdp?: string} {
  const parsed = Number.parseInt(data.remoteDeviceId ?? '', 10);
  let deviceId: number | undefined = Number.isFinite(parsed) ? parsed : undefined;
  let sdp = data.incomingSdp;
  let convoId = data.conversationId;
  try {
    const cache = require('./incomingCallCache') as typeof import('./incomingCallCache');
    const cached = cache.getIncomingCallPayload(callId);
    if (cached) {
      sdp = sdp ?? cached.incomingSdp;
      deviceId = deviceId ?? cached.remoteDeviceId;
      convoId = convoId ?? cached.conversationId;
      if (sdp) {
        console.log('[notifee] hydrated offer SDP from cache callId=', callId);
      }
    }
  } catch {
    /* cache unavailable — offer replay will deliver it */
  }
  return {
    conversationId: convoId ?? `direct:${data.fromUserId ?? ''}`,
    remoteDeviceId: deviceId ?? 1,
    incomingSdp: sdp,
  };
}
```

Do **not** log `sdp`/`convoId` values (the existing log only reports presence — keep it that way; `packages/messenger-core/__tests__/logAudit.test.ts` and the legacy mobile log-audit test gate this).

## Risk

- **The merge's `pushOverOffer` inference.** It uses "payload has no SDP" as a proxy for "this write came from the push wake". That is exact for 1:1 today (the offer is the only SDP-bearing writer) but it is an inference, not a typed source marker. If a future writer seeds an SDP-less _authoritative_ 1:1 payload, its `callerName`/`kind` would be ignored while an older entry lives. Reviewer should decide whether to accept the inference or add an explicit `source: 'offer' | 'wake'` field (larger diff, touches both call sites).
- **Stale-SDP resurrection on callId reuse.** Merge weakens "last write is the truth". The tombstone (90 s) + gateway duplicate-callId rejection cover it; a reviewer should confirm every consume path really calls `clearIncomingCallPayload` (it does today: Telecom answer keeps the entry deliberately, and the clear happens on end via `callRegistry`/`callDispatcher`/`useCall`).
- **This does not fix killed-app cold start.** In a truly-killed app the wake runs in a _separate_ JS VM with an empty cache, so there is nothing to preserve — the SDP still has to come from the queued offer replay on reconnect. NA-01 is a backgrounded-but-alive fix only; do not let the PR claim more.
- **TTL refresh on merge** (`cachedAtMs: now`) means a duplicate/retried wake extends the 60 s window. Pre-existing behaviour, intentionally unchanged here — flag if a reviewer wants it pinned to the first write.
- **Log audit.** The new helper logs only SDP _presence_, never the value, and no user/device ids beyond what already exists. Any reviewer-suggested "log the merged payload" must be rejected.
