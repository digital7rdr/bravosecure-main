# OM-06 - appendMessage lets a late-spliced OLDER message clobber the chat-list preview and re-sort the thread

## Verdict

**CONFIRMED** (drift only in line numbers; the audit's cited mechanism is exactly what the current tree does).

Evidence from the current tree (`src/modules/messenger/store/messengerStore.ts`):

- `:685-686` — the unconditional write:
  ```ts
        if (convo) {
          convo.last_message = msg;
  ```
- `:693-709` — the unconditional MRU re-sort in the same block: `const idx = s.conversationOrder.indexOf(conversationId); if (idx > 0) { ...splice... s.conversationOrder.splice(insertAt, 0, conversationId); }` — no recency test.
- `:554-565` — the very path that produces stale inserts (L18): `const tail = list[list.length - 1]; if (tail && msg.created_at < tail.created_at) { ...binary splice... } else { list.push(msg); }`. So `appendMessage` explicitly _knows_ the row can be older than the tail, then still treats it as "newest" for the conversation row.
- `:616-624` — the direct→server-UUID reroute branch has the identical defect: `serverConvo.last_message = rerouted;` followed by an unconditional `unshift`.
- The recency guard the audit points at genuinely exists elsewhere and is _not_ applied here — B-18 merge at `:472`: `if (last && (!dst.last_message || dst.last_message.created_at <= last.created_at)) { dst.last_message = last; }` and B-78 hydrate at `:1160-1165`: `if (!cur || Date.parse(cur.created_at) <= Date.parse(newest.created_at)) { convo.last_message = newest; }`.
- Display impact is real: `src/screens/messenger/conversationListOrder.ts:15` sorts the home list by `c.last_message?.created_at ?? c.created_at`, so a regressed `last_message` both rewrites the preview text/timestamp **and** re-sorts the chat down the list. `src/screens/messenger/ChatScreen.tsx:2693` (forward picker) consumes the raw `conversationOrder`, so the bogus move-to-front is visible there too.

One correction to the audit's wording: the practical symptom on **MessengerHomeScreen is the thread _sinking_, not jumping to the top** — Home re-sorts by `last_message.created_at` (B-78), so a stale preview drags the chat _down_ to the old timestamp. The bogus move-to-front on `conversationOrder` is only visible in the surfaces that read the raw order (ChatScreen's `ForwardList`). Both are wrong; the fix covers both.

## Mechanism

1. A group envelope arrives that we cannot decrypt yet (`no_key`) and is stashed in `pendingGroupEnvelopeStore`. Newer messages in the same thread decrypt and render normally, so `conversations[gid].last_message` points at (say) 12:00:30.
2. The group key lands; the stash drains. `productionRuntime.ts:6204` stamps the row's `created_at` from the sender's seal time (`sealed.aad.ts`), deliberately **not** drain time — 12:00:02.
3. `store.appendMessage(conversationId, groupMsg)` (`productionRuntime.ts:6216`) runs. `messengerStore.ts:555` sees `msg.created_at < tail.created_at` and binary-splices the row into its correct chronological slot in `s.messages[gid]` — the message list is now right.
4. Execution falls through to `messengerStore.ts:685`. `convo.last_message = msg` overwrites the 12:00:30 preview with the 12:00:02 body, and `:693-709` re-splices `gid` to the front of `conversationOrder`.
5. Result: the home row shows an _older_ message as the preview with an older timestamp, and `compareConversationsForList` (which keys off `last_message.created_at`) sinks the thread below chats that are actually less recent. The forward picker simultaneously shows it at the top. The state persists (`partialize` keeps `last_message` minus the body) until the next in-order append or a `hydrateMessages` boot pass repairs it.

Other producers of stale-but-legitimate `created_at`:

- `webrtc/callDispatcher.ts:145` — `created_at: new Date(d.at ?? Date.now()).toISOString()` for a replayed `call.missed` marker (the server holds those for `MISSED_CALL_MARKER_TTL_SEC = 6h`), so a reconnect after hours re-appends a 6-hour-old bubble.
- `webrtc/useGroupCall.ts:4342 / :4399` — missed group-call bubbles, same shape.
- `productionRuntime.ts:7232 / :7293` — 1:1 receive also derives `created_at` from `aad.ts`, so a peer with a lagging clock (or an HTTP drain of a long-dwelling envelope) hits the same path.

A subtle second case the tail-based check would miss: at boot, AsyncStorage rehydrates `conversations` (with a body-stripped but timestamped `last_message`) **before** SQLCipher `hydrateMessages` runs. A drained old envelope then appends into an _empty_ `s.messages[cid]`, so `tail` is `undefined` and the "is it older than the tail?" question answers "no" — yet it is still older than `last_message`. The guard must therefore compare against `convo.last_message`, not against the list tail.

## Fix

Single file: `src/modules/messenger/store/messengerStore.ts`. No schema change, no wire change, no persisted-shape change (`last_message` already exists in the persisted `VaultSlice`; we only change _which_ message is stored there). Nothing crypto-adjacent is touched — this is store/render-layer ordering only, which the batch architecture note explicitly allows (see OM-02 verdict: "no doc governs UI ordering keys").

### 1. New helper, placed directly after `byCreatedAtThenId`

**Anchor** (verbatim, `messengerStore.ts:76-80`):

```ts
const byCreatedAtThenId = (a: LocalMessage, b: LocalMessage): number => {
  if (a.created_at !== b.created_at) {
    return a.created_at < b.created_at ? -1 : 1;
  }
  if (a.id === b.id) {
    return 0;
  }
  return a.id < b.id ? -1 : 1;
};
```

**Insert immediately after it:**

```ts
/**
 * OM-06 — true when `next` may take over a conversation's `last_message`
 * (preview + list ordering). A late-spliced OLDER row (a stashed no_key group
 * message draining with its real send-time, a replayed missed-call marker) must
 * not regress the preview or re-sort the thread by its old timestamp. Own sends
 * always win: they are composed now, and a peer with a skewed-future clock must
 * not be able to freeze our own preview. Unparseable timestamps fall through to
 * "accept" so a malformed row can never wedge the preview permanently.
 */
const supersedesLastMessage = (cur: LocalMessage | undefined, next: LocalMessage): boolean => {
  if (!cur || next.sender_id === 'self') {
    return true;
  }
  const a = Date.parse(cur.created_at);
  const b = Date.parse(next.created_at);
  if (Number.isNaN(a) || Number.isNaN(b)) {
    return true;
  }
  return a <= b;
};
```

## Risk

Things a reviewer should be suspicious of:

1. **The `sender_id === 'self'` carve-out.** It is a deliberate deviation from a pure timestamp compare. Justification: every self append is composed at `Date.now()`; without it, one peer with a skewed-future clock would freeze _our own_ preview until wall-clock catches up. Verify no code path calls `appendMessage` with `sender_id: 'self'` and a historical `created_at` — the restore path does **not** (`backup/restoreMessages.ts:800` uses `hydrateMessages`, and its header comment at `:9` records that per-row `appendMessage` was deliberately removed). If a future restore/import path ever re-appends self rows, this clause must be revisited.
2. **`Date.parse` on `created_at`.** All producers emit `new Date(...).toISOString()`, so parsing is safe; the `Number.isNaN` fallback deliberately fails _open_ (accept the write) so a malformed row cannot permanently wedge a preview. That means a corrupt timestamp can still regress the preview once — accepted, and it is strictly not worse than today.
3. **Equal timestamps use `<=` (accept).** Intentional, and consistent with B-18 `:472` and B-78 `:1162`. It matters at boot: the rehydrated `last_message` has an empty `content` (MSG-10 strip), so an equal-ts row re-appending must be allowed to restore the preview text.
4. **`isLatest` now gates the reorder as well as the preview.** Someone may argue the MRU order should still promote on any activity. It should not: `compareConversationsForList` keys off `last_message.created_at`, so promoting the raw order while refusing the preview would leave the two orderings contradicting each other (Home says "down", ForwardList says "top"). Gating both keeps them consistent.
5. **Unread badge intentionally still bumps for a stale insert.** That is the correct product behaviour (an old-but-unseen message is unread), but it means a stale drain can produce a badge with no preview change — expected, and covered by a test.
6. **No security surface.** No crypto, AAD, sealed-sender, cert, dwell, envelope-id, or vault-MFA behaviour is touched; nothing new is logged (so `packages/messenger-core/__tests__/logAudit.test.ts` is unaffected). The only invariant nearby is MSG-10 (no plaintext body persisted), which is enforced in `partialize` and is untouched.
