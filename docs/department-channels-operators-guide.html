The database is ahead of the app. All ten migrations are applied and every rule they carry — four levels, one #broadcast per level, append-only corrections — is enforced by the database itself. Some of those rules have no screen yet, so the capability exists before the interface does.

What you can do today

  • Create your company workspace and become its admin.
  • Generate invite codes, approve or decline the people who use them.
  • Build the channel structure across four levels, each with its own posting rule.
  • Run attendance — shifts, day status, the review queue, incident reports.

What you cannot do yet

  • Monthly roster planning no screen — the server is complete; there is no calendar.
  • Attendance corrections no screen — the audit trail records changes; nothing lets you make one.
  • Rename or delete a workspace — a typo in the company name is currently permanent.

02 A to Z, in order

This is a genuine sequence — each step depends on the one before it.

  1. Hold an active Enterprise subscription

    The server refuses workspace creation without one, returning enterprise_subscription_required. This is deliberate: it is the paid gate. If the subscription lapses, the workspace disappears from your app and the server stops accepting your admin actions — the two stay in step.

  2. Create the workspace

    Messenger → Groups → Departmental Chat → Set up your workspace → Create a workspace. You name the company here. That name is what your staff and applicants see.

  3. Create your first channel

    Department Channels → Create channel. Give it a name, a type, and a posting rule. A #broadcast channel is created automatically alongside it — you do not make that one.

  4. Generate an invite code

    Approvals → generate. You get an eight-character code valid for seven days. There is nothing to find beforehand; codes do not exist until you make one.

  5. Send the code to your staff

    Any channel you like — it is just a short string. Each code can be used by many people.

  6. They request to join

    They install Bravo, go to Department Channels, tap I have an invite code, and enter it. They see your company name and nothing else.

  7. You approve them

    Approvals shows every pending request. Approving creates their membership; declining closes it. Until you approve, they are not in your organisation in any sense.

  8. Assign them to channels and shifts

    Channel membership follows the channel's access rule. Attendance is separate: create shifts and assign staff to them.

03 Invite codes

The only route into your workspace. There is no open sign-up and no directory to be found in.

PropertyBehaviour
FormatEight characters, e.g. WLVB2PN6. Generated from a cryptographic random source, not a counter.
LifetimeSeven days by default. You may set 1–90.
ReuseUnlimited people may use one code until it expires or you revoke it.
RevokingImmediate. A revoked code returns "not valid" and reveals nothing about your company.
Targeting a teamA code may be tied to one channel, so approved applicants land there automatically.
A code cannot leak your organisation. An expired, revoked or invented code returns a flat "not valid" — never a name, a size, or an acknowledgement that the company exists. Codes tied to a managers-only channel are refused at creation, not silently at approval.

04 Approving people

The most important rule in the system, and the one worth understanding precisely.

Someone who has requested to join and has not been approved sees nothing at all — no channels, no names, no attendance, not even the fact that any of it exists. This is not a filter that could be forgotten. Until you approve them, no membership record exists, so every query in the product returns nothing for them by construction.

That was verified on live data: with a request pending, the system held one request and zero membership rows. The moment you approve, the membership is created and access begins.

Declining is final for that request. There is no "undo" — the person must be sent a fresh code and apply again. This is intentional so a decline cannot be quietly reversed.

05 The four levels

Exactly four. A fifth is rejected by the database, not by the app.

LEVEL 0
EnterpriseThe company root.
LEVEL 1
MainYour primary divisions. Every channel you create today lands here unless you nest it.
LEVEL 2
SubTeams inside a division.
LEVEL 3
Sub-subThe deepest permitted. Anything below is refused.

One caveat on the labels. The database numbers the root level 1, while the channel list titles that group LEVEL 2 — MAIN. Every channel you create therefore appears under “Level 2”, and “Level 1 — Enterprise” never appears at all. The behaviour is correct and the hierarchy is sound; only the heading is off by one. It is flagged in the code as an open decision. You never set a level. You choose a parent, and the level is calculated from it. This matters: it means nobody — not the app, not a script, not a direct database edit — can flatten the tree or sneak in a fifth level. Attempting it is rejected outright.

Channels cannot be moved between parents. Deliberately, for now: moving a branch would leave everything beneath it holding a stale depth. Create it in the right place, or recreate it.

06 Who can post

Seeing a channel and being able to post in it are two separate decisions. The PDF is explicit: visibility never grants posting.

SettingWho sees itWho postsUse for
StandardAll membersEveryoneOrdinary team discussion
Read onlyAll membersManagers onlyNotices staff must read but not reply to
RestrictedManagers onlyManagers onlyAnything staff must never see
Standard and Read only look identical in the database — they differ only in the posting rule. An early version of the editor could not read that rule, so opening any channel and pressing Save silently promoted every member to poster. That is fixed, but it is why the setting is always shown explicitly rather than inferred.

07 The #broadcast channel

Created for you, at every level, and it cannot be removed.

  • Automatic. You never create one. Making your first channel at a level creates the #broadcast for that level too.
  • One per level. A second is rejected by the database.
  • Announcement only. Managers post; staff read. Attempting to relax this is overridden — the setting is pinned, not merely defaulted.
  • Undeletable. Enforced at the database, so it holds regardless of which part of the app asks.
Every workspace now has one. Automatic creation originally ran only when a channel was made, so organisations created before the feature had none. A one-off migration on 5 August 2026 created the missing channels and seeded their membership, taking staging from 1 of 18 organisations covered to 18 of 18. Creating a workspace now seeds it as well, so a brand-new company has its #broadcast from the first moment — that gap was found by walking the flow on a device, not by a test.

A branch manager is scoped to their branch. They see and act on their own department only — including sensitive records such as sick leave. That scoping is applied on the server to every read, and to leave and day-status records it resolves through the person's own department rather than the shift's, so records with no shift attached stay protected.

09 Attendance

Working now live

  • Shifts — create, edit, assign staff, archive.
  • Day status — mark someone Leave, Sick leave, Off duty or Absent.
  • Review queue — approve or reject check-ins that fell outside the site or the time window.
  • Staff view — each person sees their own shift and history.

Built on the server, no screen yet not usable

  • Monthly roster — plan a whole month as Draft, check it for double-bookings, then Publish. Drafts are invisible to staff until published. Complete and tested server-side; there is no calendar to drive it.
  • Corrections — change an attendance record while keeping the original forever, with who changed it, when, and why. The record is permanent: it cannot be edited, deleted, or wiped, even by a direct database command.
Two statuses from the specification are missing: Emergency Leave and Mission. Four of the six are implemented.

11 Before real customers

Honest list, worst first. These came from testing the running system, not from reading the code.

  1. Roster planning and attendance corrections have no screens still open

    Both are specified as mandatory and both are server-complete: the rules, the tables and the append-only audit trail all exist and are enforced. There is no calendar to plan a month with, and no form to make a correction. This is the largest remaining gap.

  2. A workspace cannot be renamed or deleted still open

    A typo in the company name is permanent, and every employee sees it. There is no route for either action.

  3. If a subscription lapses, appointed managers keep full access needs a decision

    The owner loses access and then cannot remove them, because revoking requires the controls they just lost. Awaiting a decision on what should happen to a lapsed owner's managers.

  4. The channel list labels the first level "Level 2"

    The database numbers the root level 1 while the heading reads LEVEL 2 — MAIN, so "Level 1 — Enterprise" never appears. Behaviour and hierarchy are correct; only the heading is off by one. Flagged in the code as an open decision rather than settled.

Closed on 5 August 2026

Each was fixed, deployed to staging and then verified against the running system — eighteen checks end to end, plus a walk through the app on two devices.

  1. The sign-up route now reaches the workspace screens

    The create-or-join fork waits for the product tree to mount before navigating, because the paywall unmounts and the tree mounts in the same tick and an immediate navigate was silently dropped.

  2. Buying the subscription no longer grants admin authority

    Removed from both places that decided it. Verified live: an Enterprise account with no workspace reports is_org_manager: false, and creating the workspace is what makes them an admin.

  3. Channel notifications open the department screen

    Not the ordinary chat screen with its call buttons. The same rule now also decides the in-app list taps, so the two cannot drift apart.

  4. Department channels no longer appear in the messenger lists

    They were filtered by a network call, which cannot hide anything until it returns — so they were visible on every cold boot and all session when offline. The filter now reads local state.

  5. Every workspace has its #broadcast

    Staging went from 1 of 18 organisations covered to 18 of 18, and new workspaces are seeded on creation.

  6. Staff can no longer react, reply or edit in #broadcast

    Reactions and edits were sealed-sender fan-outs to every member and were ungated. Promoting a member to poster there is refused by the server with a 403.

  7. The Professional plan is gone from Enterprise sign-up

    Confirmed on a device: the plan list shows only Lite and Enterprise.

  8. "CPO" and "Employee" wording replaced

    Enterprise surfaces read "Member" throughout.

  9. Channel lists are paged

    Bounded with a cursor, verified against the live endpoint.

  10. Lists show real errors instead of an empty screen

    Offline, "no access" and a server fault now give three different answers with different actions, across ten lists.

    11. One thing worth knowing about failures. Lists used to turn every error into an empty screen, so "no access", "offline" and "something broke" were indistinguishable from "nothing here" — the single most reliable way to get a fault misdiagnosed in the field. Ten lists now answer each case differently and offer the matching action. The screens listed as still open are the ones this has not reached.
