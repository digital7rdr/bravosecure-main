# iOS Build Runbook

First verified green: 2026-07-16 (Xcode 26.6, iOS 26.5 SDK, CocoaPods 1.17, RN 0.81.5 / Expo SDK 54).

## TL;DR

```sh
npm install                      # applies patches/ via patch-package (required)
cd ios && pod install            # Podfile exports USE_FRAMEWORKS from Podfile.properties.json
xcodebuild -workspace BravoSecure.xcworkspace -scheme BravoSecure \
  -configuration Debug -destination 'generic/platform=iOS Simulator' build
```

`npm run ios` (expo run:ios) works too once pods are installed.

## Required configuration (already in place — do not regress)

| Setting                                                   | Value                                | Why                                                                                                    |
| --------------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| `ios.deploymentTarget` (app.json → expo-build-properties) | `15.5`                               | GoogleMLKit 8 (face detection) requires ≥ 15.5                                                         |
| `ios.useFrameworks`                                       | `static`                             | Firebase Swift pods cannot build as static libraries                                                   |
| `ios.buildReactNativeFromSource`                          | `true`                               | Expo 54's prebuilt React-Core has no module maps → breaks under use_frameworks                         |
| `ENV['USE_FRAMEWORKS']` export in `ios/Podfile`           | derived from Podfile.properties.json | RN's `install_modules_dependencies` only adds React\_\*.framework header paths when the env var is set |

The same values are mirrored in `ios/Podfile.properties.json` (gitignored, regenerated by prebuild from app.json).

## patch-package patches that exist for iOS (in `patches/`)

- `@op-engineering+op-sqlite` — exclude bundled libsql xcframework headers (duplicate `libsql.h` under frameworks).
- `@stripe+stripe-react-native` — `STPPaymentStatus` fwd-decl NSUInteger→NSInteger (hard error on Xcode 26).
- `react-native-quick-crypto` — podspec HEADER_SEARCH_PATHS + qualify `logs.h` includes (headermap name-collision with React-utils). iOS-only branches; Android unaffected.
- `react-native+0.81.5` — fmt 11.0.2 consteval disabled via prepare_command (Xcode 26 clang bug, fixed upstream in fmt 11.1) + React-utils `platform/ios` header path in `new_architecture.rb`.
- `react-native-argon2` — SWIFT_INCLUDE_PATHS so Xcode 26's explicit-module build resolves the transitive `argon2` clang module.
- `expo-constants` — quote `$PODS_TARGET_SRCROOT` in the script phase (repo path contains a space).

The generated `ios/BravoSecure.xcodeproj` also carries a quoting fix in the
"Bundle React Native code and images" phase (unquoted `react-native-xcode.sh`
path breaks on the space in "Office Work"). If you ever regenerate ios/ via
prebuild, re-apply it (run the failing phase once to see the exact line).

### `ENABLE_USER_SCRIPT_SANDBOXING` must be NO

Symptom — Debug builds fail (Xcode GUI and plain `xcodebuild` alike):

```
Sandbox: bash(NNNNN) deny(1) file-write-data
  …/Build/Products/Debug-iphoneos/BravoSecure.app/ip.txt
```

RN's `react-native-xcode.sh` writes the dev machine's LAN IP into the built
bundle (`echo "$IP" > "$DEST/ip.txt"`, line 27) so the dev client knows where
Metro is. Xcode 26 defaults `ENABLE_USER_SCRIPT_SANDBOXING` to `YES`, which
forbids a script phase writing to anything it hasn't declared as an output —
so the phase dies.

Fixed in `ios/BravoSecure.xcodeproj/project.pbxproj` (both Debug and Release
project-level configs set to `NO`). **ios/ is gitignored — `expo prebuild`
resets this to `YES`.** Re-apply after any regeneration:

```sh
sed -i '' 's/ENABLE_USER_SCRIPT_SANDBOXING = YES;/ENABLE_USER_SCRIPT_SANDBOXING = NO;/g' \
  ios/BravoSecure.xcodeproj/project.pbxproj
```

Passing `ENABLE_USER_SCRIPT_SANDBOXING=NO` to `xcodebuild` works too, but only
for CLI builds — the Xcode GUI has no equivalent, so the project setting is the
real fix.

> **Close Xcode before editing `project.pbxproj` by hand.** Xcode holds the
> project in memory and rewrites it on its own schedule, silently reverting
> external edits. This has already cost this project its bundle ID and team
> settings once.

### ⚠️ Regenerating a patch after an Android build sweeps in build artifacts

`patch-package` diffs the **whole package directory** against the pristine npm
tarball. If you have run an Android build, packages with native code hold Gradle
and CMake output (`android/build/**/*.dex`, `android/.cxx/**` — CMakeCache,
`.ninja_deps`, `.o` binaries) that is _not_ in the tarball, so patch-package
records all of it as additions.

This is not theoretical: the first cut of these patches was **9 MB across 1,300+
files** (op-sqlite alone was 4.7 MB / 575 files for a one-line podspec change).
Committed, they would have injected stale `.dex` and `.cxx` output into every
teammate's `node_modules` on `npm install`.

Before regenerating, delete the **build output only**:

```sh
rm -rf node_modules/<pkg>/android/build node_modules/<pkg>/android/.cxx
npx patch-package <pkg>
```

**Do not delete a bare `node_modules/<pkg>/build`.** For JS packages that is the
_shipped_ compiled output, not build junk — `expo-constants` ships its JS there.
Deleting it makes patch-package record 20 file deletions, and the resulting patch
wipes the package's JS on every install. Recover with
`rm -rf node_modules/<pkg> && npm install`.

Sanity check every regenerated patch before committing — these should be small:

```sh
grep -c '^diff --git'      patches/<name>.patch   # expect 1–4 files
grep -c '^deleted file mode' patches/<name>.patch # expect 0
```

Reference sizes: every patch here is under 3 kB except `expo-constants` (~800 B)
and the pre-existing `react-native-webrtc` (6.1 kB). Anything in the megabytes is
wrong.

## ⚠️ Firebase: real plist, but bundle ID is unsettled

**Updated 2026-07-17.** The placeholder is gone — `GoogleService-Info.plist` (repo root,
copied to `ios/BravoSecure/`) is the real one: project `bravo-734da`, registered for
bundle ID **`com.bravosecure.app`**. Analytics and Crashlytics work.

Push does NOT work, and the bundle ID is likely to change to `com.bravosecure.mobile`.
**Read [`docs/runbooks/IOS_README.md`](IOS_README.md) before touching iOS signing** — it covers
the App ID conflict, the bundle-ID split decision, and the APNs steps.

Short version: the plist must match whatever `PRODUCT_BUNDLE_IDENTIFIER` the binary is
actually signed with, or Firebase init fails at launch. The Xcode project and the plist
currently disagree (project says `.mobile`, plist says `.app`); builds only line up
because the bundle ID is passed as a command-line override.

`app.json` sets `ios.googleServicesFile: "./GoogleService-Info.plist"`, so
`npx expo prebuild -p ios` wires it automatically (prebuild FAILS without this file —
the RNFB plugin throws).

## ⚠️ Stale `node_modules` kills the archive at the LAST phase (build 163)

The Metro bundle ("Bundle React Native code and images") is the **final** phase of
the archive. An unresolvable import therefore fails ~25 minutes in, after all 184
pods have compiled — the most expensive possible place to learn about a missing
dependency.

Build 163 died exactly this way:

```
error: Unable to resolve module @react-native-firebase/app-check from
  src/modules/messenger/push/appCheckHeader.ts
** ARCHIVE FAILED **
```

`@react-native-firebase/app-check` had been in `package.json` **and**
`package-lock.json` since `3641b2e9`, but `npm install` was never run on the
build machine — `node_modules/@react-native-firebase` was two months stale.

**The fail-soft `require()` does not protect you here.** `appCheckHeader.ts`
wraps its `require()` in a lazy try/catch so a build without the _native_ module
degrades to `{}`. But Metro resolves `require()` **statically at bundle time**, so
a package absent from `node_modules` is a hard bundler error, not a soft degrade.
Runtime fail-soft and bundle-time resolution are different problems.

Two pre-flight guards now catch this before the compile (`scripts/ios-release.sh`):

- **G6** — every key in `package.json` `dependencies` exists in `node_modules/`.
- **G7** — if the app-check JS package is installed, `RNFBAppCheck` must be in
  `ios/Podfile.lock` (JS present + pod missing = bundles fine, missing at runtime).

Both are mutation-proven: each goes red under the exact broken state.

Cheap independent pre-check when touching dependencies — ~50s instead of ~25min:

```sh
npx expo export:embed --platform ios --dev false --entry-file index.js \
  --bundle-output /tmp/check.jsbundle --assets-dest /tmp/bundle-assets
```

After `npm install` adds a package with a native iOS half, you **must** also run
`(cd ios && pod install)` or the module is missing at runtime. Verify the pod
install did not regress `ENABLE_USER_SCRIPT_SANDBOXING` (expect 4 × `NO`, 0 × `YES`).

> `pod install` may need to clone `firebase-ios-sdk`. If it dies with
> `RPC failed; curl 92 HTTP/2 stream ... CANCEL` / `fatal: early EOF`, that is
> transient: `git config --global http.version HTTP/1.1` and retry.

## Known limitation: no simulator RUN on Apple Silicon

`@react-native-ml-kit/face-detection` → GoogleMLKit ships **no arm64-simulator
slice** (device arm64 + x86_64 sim only) and forces `EXCLUDED_ARCHS arm64` for
simulator builds, so the app builds x86_64-only for simulators. Xcode 26's
iOS 26.5 simulator runtime no longer accepts x86_64 (Rosetta) apps — install
fails with "Failed to find matching arch".

Consequences:

- **Build/CI verification on simulator: works** (this is what we gate on).
- **Running/debugging: use a real iPhone** (device slices are complete), or drop the MLKit face-detection dependency on iOS (product decision — it powers the selfie/liveness check).
- EAS cloud iOS builds (`npm run eas:build:ios:*`) target devices, so they are unaffected by the simulator limitation, but still need the real Firebase plist checked in or supplied as an EAS file secret.

## Node in Xcode script phases

`ios/.xcode.env.local` (machine-local, gitignored) pins `NODE_BINARY` to the
volta-managed node. Recreate it on a new machine if script phases can't find
node: `echo "export NODE_BINARY=$(command -v node)" > ios/.xcode.env.local`.

## Cut + upload a TestFlight build

The proven local pipeline (used for builds 142 and 143). Signing is manual with
the org distribution cert + "Bravo Secure App Store" profile; upload uses the
App Store Connect API key `AuthKey_S6379ZCA56.p8` (issuer in `asc.py`).

```sh
# 1. Set version/build. Info.plist is HARDCODED (not $(MARKETING_VERSION)),
#    so xcodebuild -showBuildSettings overrides are IGNORED — edit the plist:
/usr/libexec/PlistBuddy -c "Set :CFBundleShortVersionString 1.0.115" ios/BravoSecure/Info.plist
/usr/libexec/PlistBuddy -c "Set :CFBundleVersion 143"               ios/BravoSecure/Info.plist

# 2. Archive (Release = distribution cert + App Store profile). ~20-30 min.
xcodebuild -workspace ios/BravoSecure.xcworkspace -scheme BravoSecure \
  -configuration Release -destination 'generic/platform=iOS' \
  -archivePath /tmp/BravoSecure.xcarchive archive

# 3. Export a signed .ipa (re-signs; ~2 min). exportOptions.plist = app-store-connect method.
xcodebuild -exportArchive -archivePath /tmp/BravoSecure.xcarchive \
  -exportOptionsPlist exportOptions.plist -exportPath /tmp/ipa-export

# 4. Upload. READ THE LOG — a wrapper `echo $?` can report 0 while altool exits 1.
xcrun altool --upload-app -f /tmp/ipa-export/BravoSecure.ipa -t ios \
  --apiKey S6379ZCA56 --apiIssuer <issuer-id>   # look for "UPLOAD SUCCEEDED"
```

Then in App Store Connect the build processes (~5-15 min) → answer export
compliance once (see below) → TestFlight → Internal Testing → add testers. No
Beta App Review for internal testers.

### ⚠️ Export-compliance trap — altool error 90592

Symptom on upload:

```
UPLOAD FAILED — 90592: Invalid Export Compliance Code. The export compliance
key value [] in the app's Info.plist doesn't match ... export compliance
documentation. To find the correct value, go to My Apps on App Store Connect.
```

Cause: App Store Connect already holds a saved export-compliance answer (with a
generated compliance code) for this app. Baking `ITSAppUsesNonExemptEncryption`
into the Info.plist **without** the paired `ITSEncryptionExportComplianceCode`
makes Apple see an empty code (`[]`) where it expects the saved one → reject.

Fix (do NOT bake the key in for the ASC-UI compliance flow): strip it and
re-export — **no recompile needed**, and the rejected build number is NOT
consumed (rejection is pre-ASC), so reuse it:

```sh
/usr/libexec/PlistBuddy -c "Delete :ITSAppUsesNonExemptEncryption" \
  /tmp/BravoSecure.xcarchive/Products/Applications/BravoSecure.app/Info.plist
# also delete from ios/BravoSecure/Info.plist and app.json ios.infoPlist
xcodebuild -exportArchive -archivePath /tmp/BravoSecure.xcarchive \
  -exportOptionsPlist exportOptions.plist -exportPath /tmp/ipa-export-fixed
xcrun altool --upload-app -f /tmp/ipa-export-fixed/BravoSecure.ipa -t ios \
  --apiKey S6379ZCA56 --apiIssuer <issuer-id>
```

Export compliance is then answered in the ASC UI (encryption → "Yes, qualifies
for exemption", the mass-market self-classification path for the E2EE stack).
Only bake `ITSAppUsesNonExemptEncryption` back into Info.plist if you ALSO add
the matching `ITSEncryptionExportComplianceCode` from ASC.
